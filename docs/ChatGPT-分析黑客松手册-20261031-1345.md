# Agent Native × System 1：重新思考 AI 教育的核心痛点

我认为这里存在一个值得探索的产品方向：

**当前 AI 教育主要在帮助人们“理解知识”和“完成任务”，但教育更深层的目标之一，是让学习者在没有 AI 辅助的真实环境中，也能自主、及时、正确地行动。**

两者不是同一个目标。

例如：

- 学生理解了英语语法，却不能在真实对话中流畅表达。
- 一个人掌握了沟通技巧，却无法在突然发生的社交互动中运用。
- 程序员能解释死锁的四个条件，却不能在复杂程序运行时及时识别死锁风险。
- 学生学会了数学解题步骤，却无法在陌生问题中迅速识别合适的方法。

这些问题具有一个共同特征：

**学习者拥有某种显性知识，但这种知识尚未转化为能够根据情境自动启动的能力。**

这就涉及 System 1、System 2、技能自动化（Automaticity）、知识迁移（Transfer of Learning）与 Agent Native 的交叉。

## 一、先建立正确的认知模型

**System 1 / Type 1**

快速、自动化的处理

- 情境识别
- 联想与模式匹配
- 习惯性反应
- 已熟练化的技能
  
  通常较少依赖工作记忆和有意识控制

**System 2 / Type 2**

审慎、受控的处理

- 逻辑推理
- 规则学习
- 假设与规划
- 有意识地纠错
  
  通常更依赖注意力与工作记忆

需要特别严谨地指出：System 1 和 System 2 并不是大脑中两个独立运行的实体。现代双过程理论更倾向于将它们理解为不同类型的认知加工过程，其中 Type 1 本身包含多种不同机制。\[[Dual-Process Theories of Higher Cognition: Advancing the Debate](https://pubmed.ncbi.nlm.nih.gov/26172965/?utm_source=chatgpt.com); [Dual Process Theories: Computing Cognition in Context](https://doi.org/10.1145/3487055?utm_source=chatgpt.com)\]

教育的目标也不是简单地让所有 System 2 过程转变成 System 1。相反，成熟的技能往往需要：

1. 在熟悉情境中高效调用已经掌握的模式。
2. 在遇到异常、不确定性或高风险决策时，及时转向审慎分析。
3. 知道什么时候应该停止自动反应，重新检查自己的判断。

因此，我们真正要研究的是：

**教育如何改变学习者在具体情境中的行为策略，而不仅仅改变其能够陈述的知识。**

## 二、我认为最核心的六个痛点

### 痛点 1：知识习得与行为能力之间存在断裂

传统教育以及大量 AI Tutor 都非常擅长回答：

> 学生是否理解了某个概念？

但更难回答：

> 当学生遇到某个具体情境时，能否独立地识别它、调用正确知识并采取行动？

这其实涉及三个不同的能力：

**Declarative Knowledge - 陈述性知识**

能够解释规则、原理和操作方法。

**Procedural Skill - 程序性技能**

能够在任务中实际执行相应操作。

**Contextualized Automaticity - 情境化自动执行能力**

在合适的情境下，能够以适当速度、较少认知负担地启动并执行技能。

传统学习评估经常集中在前两层，而第三层更难被充分观察。

**Agent Native 的潜在机会：** 不再要求学生描述自己会什么，而是直接创造情境，让学生实际做出来，观察其行为，再调整训练内容。

但注意：并不是每一种能力都应该自动化。对于复杂数学证明，速度甚至不应该是主要目标。

### 痛点 2：知识迁移（Transfer）没有被真正解决

我认为这是所有痛点中最根本的一个。

学习发生在训练情境 $D_{\text{train}}$ 中，但能力最终需要在真实情境 $D_{\text{real}}$ 中表现出来。

如果两种情境的刺激、干扰、任务结构差异很大，那么：

$$
P(\text{成功}\mid D_{\text{train}})
$$

很高，并不代表：

$$
P(\text{成功}\mid D_{\text{real}})
$$

也很高。

例如，学生可以在 AI 对话中反复练习英语，但真实场景可能出现不同口音、噪声、打断、话题突然改变、多个说话者同时讲话。

**今天的 AI 已经能大量生成练习，但生成练习不等于实现知识迁移。**

一项 2026 年发表的课堂学习元分析汇总了 53 项研究，发现提取练习、间隔练习和交错练习总体上有益，但这些收益并不能不加区分地推广到理解与迁移任务；练习所调用的认知过程是否符合目标任务，十分关键。\[[A Meta-Analysis of the Effectiveness and Boundary Conditions of Retrieval Practice, Distributed Practice, and Interleaved Practice in Authentic School Classrooms \| Educational Psychology Review](https://link.springer.com/article/10.1007/s10648-026-10225-5?utm_source=chatgpt.com)\]

这意味着未来的教育 Agent 不能只是动态出题，而必须探索：

- 怎样的情境变化能促进泛化？
- 哪些技能只在熟悉环境中有效？
- 如何发现学习者记住的是固定答案，而不是通用策略？
- 如何设计从熟悉场景到陌生场景的训练分布？

### 痛点 3：真实情境存在不可忽略的反应时限

这与你之前提出的 System 1 社交互动问题尤其相关。

假设一个学生正在参加小组讨论，突然有人质疑他的意见。

他可能知道如何组织论证，但真正作出回应还需要经历：

感知信息

识别情境

选择策略

组织表达

作出回应

在即时对话中，每个环节都可能影响交互效果。

传统 AI Chatbot 存在两层时延问题：

1. **计算时延：** AI 获取上下文、推理、输出建议需要时间。
2. **认知时延：** 即使 AI 立刻给出答案，学习者仍需阅读、理解、判断和执行。

第二层经常被忽略。

即使我们将模型端推理时延压到极低，也不意味着人能在真实互动中实时使用建议。

因此，教育 Agent 的最佳策略可能不是在真实场景中不断提醒，而是**在真实场景发生之前，帮助学习者形成能够自主启动的行为策略**。

这也是为什么模拟训练可能比实时提示更有教育价值。

### 痛点 4：学习者已经形成的自动反应难以改变

System 1 相关的教育问题不只有“还没有形成技能”。

还有另一种情况：**已经形成了一种不理想的习惯性反应。**

例如：

- 面对突发问题时习惯性回避。
- 听到他人的反对时，立即进入防御性回应。
- 编程调试时总是首先怀疑某个熟悉的错误来源，忽略其他可能性。
- 阅读英文时习惯性逐词翻译，影响即时理解。

这类问题不能仅通过解释正确方法解决。

因为问题可能不是缺乏显性规则，而是旧的反应模式在具体情境中仍然占据优势。

这就形成了一个教育需求：

**不仅要建立新的技能，还要识别旧反应被什么触发，并训练更合适的替代反应。**

Agent 可以在低风险环境中重复构造相似但不完全相同的触发情境，并观察行为变化。不过，在真实生活中改变稳定的习惯通常需要更长时间，不能简单假设几次对话就能完成。

### 痛点 5：传统反馈缺乏情境和时间精度

对于某些技能，只有结果反馈是不够的。

比如：

“这次演讲得了 80 分。”

这个反馈的信息量很低。

如果系统能指出：

- 哪一句话之后听众可能开始困惑；
- 学习者在哪个问题上出现了明显迟疑；
- 哪一次打断后话题失去了原有结构；
- 是由于知识不足、情境识别错误，还是表达组织困难；

就更有可能支持针对性训练。

AI Agent 的机会在于将连续行为分解为可分析的事件，并选择恰当的反馈时机。

但也必须承认：**模型推测的情绪、意图、社交效果不能直接当作客观事实。** 尤其是从表情、语气推断心理状态时，误判风险较高。

### 痛点 6：AI 帮学生完成任务，却可能削弱其自主学习

这是 Agent Native 教育必须正面面对的矛盾。

一项发表于 2025 年《PNAS》的研究，在近千名高中数学学生中比较了不同 AI 辅导方式：

GPT Base 组，AI 辅助练习成绩相对对照组

# \+48%

GPT Base 组，移除 AI 后独立考试成绩

# \-17%

均为研究报告的相对变化，不代表所有 AI 教育产品的普遍效果。

提供教学引导而不是直接答案的 GPT Tutor 版本，大幅减轻了独立考试表现下降的问题，但研究也没有发现它带来明确的独立考试正向提升。\[[Generative AI without guardrails can harm learning: Evidence from high school mathematics](https://doi.org/10.1073/pnas.2422633122?utm_source=chatgpt.com)\]

这揭示了一个重要的目标冲突：

**提高 AI 辅助下的任务表现，与提高学习者自身能力，并不总是一致。**

传统生产力 Agent 追求替用户完成更多任务。

但教育 Agent 有时必须主动减少自己的帮助。

这不是一个普通的 Prompt 技巧，而是需要体现在整个产品目标、交互机制与评估方式中的设计原则。

## 三、为什么这些问题需要 Agent Native？

这里必须区分两个概念：

**AI Tutor + Agent 功能**：在现有 AI 教师上增加工具调用、记忆、出题等能力。

**Agent Native Education**：从一开始，就把学习过程设计为 Agent 持续观察、决策、干预与评估的闭环。

真正的差异不在于使用多少个 Agent，而在于谁负责组织学习过程。

传统 AI Tutor

学生提出问题

AI 提供解释

对话结束

---

Agent Native Education

建立学习者能力模型

知识、技能、历史表现、不确定性

自主选择并生成训练情境

难度、变化、干扰、时间约束

观察学习者的实际反应

行为、正确性、时机、纠错过程

诊断与选择教学干预

提示、复盘、变式训练、撤除辅助

持续更新能力估计，直到独立迁移测试

这个 Agent 的核心不是产生更多知识，而是决定：

**学习者下一次应该经历什么，才能最有效地改善其自主行为？**

### 人类 System 1 与 AI 的快慢双环

还可以进一步设计两种不同时间尺度的 Agent 工作过程。

|  | 快环：实时互动 | 慢环：教学规划 |
|--------|--------|--------|
| 工作内容 | 识别发言、响应互动、维持情境 | 分析错误、调整策略、更新能力模型 |
| 延迟要求 | 尽量低 | 可以容忍较长推理时间 |
| 主要模型 | 实时语音或轻量化模型 | 推理模型、评估器、记忆系统 |
| 教育目标 | 提供接近真实场景的练习 | 决定如何改善下一轮练习 |

这里的“快环”与“慢环”是工程架构，不等同于人类的 System 1 和 System 2。

而且我认为**慢环甚至可以比快环更重要**：实时对话模型负责呈现情境，深度推理模型负责教学决策。这样不必为了复杂的实时推理牺牲交互自然度。

## 五、真正应该优化的指标是什么？

我想进一步指出一个容易犯的错误：

**我们不能仅通过学习者的反应速度判断 System 1 相关教育是否成功。**

比如，面对一个复杂的伦理问题，立即回答可能反而是错误的。最好的能力有时是意识到自己需要停下来思考。

所以我们可以把学习目标形式化为：

$$
\max_{\pi_{\mathrm{learner}}}
\mathbb E_{s\sim D_{\mathrm{real}}}
\left[U(\pi_{\mathrm{learner}}(s),s)\right]
$$

其中：

- $s$：真实情境，包括上下文、刺激和时间约束。
- $\pi_{\mathrm{learner}}$：学习者在没有 AI 辅助时的行为策略。
- $U$：综合评价行为是否恰当、正确、安全、及时的效用函数。

与一般 AI Agent 最大的差异是：**这里优化的对象不是 Agent 的策略，而是学习者自身的策略。**

这也引出一个很好的产品评估方法：

训练有效性验证

前测

无辅助

自适应训练

反馈逐步减少

迁移测试

陌生场景、无辅助

评价指标：行为恰当率、错误类型、有效反应时间、跨场景稳定性，以及延迟测试后的保持程度。

尤其要强调，真实迁移仍然是一个研究难题。2026 年关于 AI 虚拟患者沟通训练的系统综述发现，模拟训练具有积极潜力，但能力能否可靠迁移到真实临床环境，仍然缺乏充分证据。\[[Use of artificial intelligence–enhanced virtual patients in educational approaches to medical interview training: a systematic review](https://pmc.ncbi.nlm.nih.gov/articles/PMC13067467/?utm_source=chatgpt.com)\]

这意味着一个产品不能只展示“训练后分数上升”，就宣称改变了人的真实行为。

## 六、如果把它做成一个黑客松产品

我会尝试一个暂称 **ReflexLab** 的概念：面向真实场景的自适应技能训练 Agent。

用户可以选择一个目标，例如“在小组讨论中表达不同意见”。

系统先提供一段简短的显性知识教学，然后进入实时情境模拟。AI 扮演不同立场的队友，动态打断、追问或改变话题，观察学习者如何应对。

随后，教学 Agent 根据这次互动中的具体问题，决定下一轮应该重复什么、改变什么、撤除什么辅助。

最重要的展示环节不是 AI 的对话能力有多强，而是：

**同一个用户在面对未见过的情境时，是否比训练前更能自主地作出恰当反应。**

在这次 41 小时开发窗口内，可以实现一个前测、情境训练、自适应复练、无辅助后测的完整闭环。至于长期技能自动化和现实迁移，可以作为需要后续实证验证的研究目标，而不是黑客松期间就声称已经解决的问题。

## 七、我认为还有一个更深层的产品哲学

大多数 AI 产品追求让 AI 变得越来越不可替代：更多任务交给 AI，更多决策依赖 AI。

但教育 AI 存在一种相反的成功标准：

**一个优秀的教育 Agent，最终应该能够让学习者越来越不需要它。**

如果这个判断成立，那么我们甚至可以将教育 Agent 的核心机制定义为 *Scaffolding and Fading*（支架式支持与逐步撤除）：

最初由 Agent 提供大量支持，随后逐渐减少外部辅助，直到学习者可以独立解决问题。

这不意味着完全抛弃 AI。更合理的目标是：让学习者保有必要的自主判断与核心能力，同时有效利用 AI 处理其他工作。

我认为真正值得研究的，是这个问题：

**我们能否让 Agent 不再主要负责生成答案，而是负责设计经历，通过持续的情境交互，改变学习者自身的认知与行为能力？**

这才是 System 1 与 Agent Native Education 结合时最有研究价值的交叉点。它超出了传统的知识问答，也超出了简单的 AI 角色扮演。

## 一、从第一性原理重新定义问题

人在执行一项任务时，存在三个客观限制：

1. **观察限制**：无法同时注意到环境中的全部相关信息。
2. **计算限制**：工作记忆、注意力和即时推理能力有限。
3. **时间限制**：许多行为必须在特定时间窗口内完成。

例如，演讲时需要同时组织语言、观察听众反应、回忆论证结构并控制语速。这些过程争夺有限的认知资源。

所以我们可以提出一个更一般的产品命题：

> 当用户正在执行任务时，一个持续观察环境、理解用户目标、判断当前状态，并在适当时机提供最小必要干预的 AI Agent，能否改善人的实时行为表现？

这里的关键词不只是实时推理，而是 **持续感知、主动判断、即时干预、闭环反馈**。

## 二、RealtimeGuide 的核心不是聊天，而是控制闭环

**Perception：持续感知**

屏幕、麦克风、摄像头、笔迹、键盘事件、任务进度

**Inference：状态理解与预测**

用户正在做什么？目标是什么？是否偏离？接下来可能发生什么？

**Policy：决定是否干预**

沉默、提醒、提示、纠错、暂停指导，还是等待更合适的时机？

**Intervention：即时干预**

浮层、视觉提示、语音、触觉信号、逐步指导

观察用户是否响应干预，再更新状态与策略

这个架构的关键区别是：用户不需要主动提出问题。

Agent 可以主动发现一个值得干预的事件。

但是有一个十分重要的原则：

**持续监测 ≠ 持续干预。**

甚至可以进一步区分：

- 持续监测：始终保持对任务状态的感知。
- 实时推理：在新信息出现时，增量更新状态和判断。
- 主动干预：只有当预期收益超过打断成本时，才提供指导。

这第三步，可能才是 RealtimeGuide 最有价值的技术核心。

## 三、三个场景其实共享同一个底层问题

**场景 A：社交 RealtimeGuide**

Agent 通过授权的语音或文字流理解对话，识别用户是否遗漏对方的问题、偏离话题或需要组织回应。

即时建议示例：「先回应对方提出的问题」「可以追问一个细节」。

核心困难：对话反应窗口短，不能让 AI 提示本身增加过多认知负担。

---

**场景 B：做题 RealtimeGuide**

Agent 观察逐步推导、笔迹或编辑器事件，维护对当前解题状态的理解，在发现可验证的逻辑错误或明显卡顿时介入。

即时建议示例：「你刚才平方后，是否需要讨论另一种符号情况？」

核心困难：如何在纠正错误的同时，不直接替学生完成思考。

---

**场景 C：演讲 RealtimeGuide**

Agent 同时分析语音与演示文稿内容，判断讲话速度、内容结构、时间分配及论点是否清晰。

即时建议示例：「距离结束还有一分钟，尽快回到核心结论」。

核心困难：判断什么问题值得在演讲过程中提示，而不是留到复盘。

这三个场景的共同点不是教育内容，而是：

**用户存在持续变化的任务状态，而传统 AI 往往缺少对状态的持续感知和主动干预。**

因此，RealtimeGuide 可以有统一的 Agent Core，而不同的任务只需要更换感知适配器、领域验证器和干预策略。

## 四、真正值得研究的是 Intervention Policy

从形式化角度，可以把系统视为一个部分可观察的序贯决策问题。

设：

- $s_t$：用户在时刻 $t$ 的真实任务与认知状态（无法直接完整观测）。
- $o_t$：屏幕、语音或操作记录等可观察信息。
- $b_t$：Agent 根据历史观测形成的状态估计。
- $a_t$：Agent 选择的干预行为。

那么核心优化目标可以写作：

$$
a_t^*=\arg\max_a
\mathbb E[
\Delta U_{\text{task}}
+\lambda \Delta U_{\text{learning}}
-C_{\text{interrupt}}
-R_{\text{error}}
\mid b_t,a]
$$

这里有四项需要平衡：

| 因素 | 解释 |
|--------|--------|
| 任务收益 | 这次提示能否改善当前任务表现 |
| 学习收益 | 这次提示是否有助于用户形成自主能力 |
| 打断成本 | 提示是否分散注意力、干扰正在进行的思考 |
| 错误风险 | AI 判断错误时，会造成多大负面影响 |

因此，RealtimeGuide 最有意思的能力可能不是判断“用户哪里错了”，而是判断：

**现在提醒是否比不提醒更好？**

例如用户在做数学题，刚刚写下一个错误步骤，但正在自己检查。

立即弹出正确答案，可能会打断他的自我纠错过程。

此时最优干预可能是沉默。

这也与已有的运动学习研究中关于反馈依赖的发现一致：高频实时反馈可能提高练习时表现，却不一定有利于撤除反馈后的学习保持。但这种证据不能直接推广为所有认知学习任务的确定规律。\[[Learning Gait Modifications for Musculoskeletal Rehabilitation: Applying Motor Learning Principles to Improve Research and Clinical Implementation \| Physical Therapy](https://academic.oup.com/ptj/article/101/2/pzaa207/6043919?utm_source=chatgpt.com); [Effects of self-control of feedback timing on motor learning](https://pmc.ncbi.nlm.nih.gov/articles/PMC12491054/?utm_source=chatgpt.com)\]

## 五、System 1 在这里发挥什么作用？

我认为 System 1 不是 RealtimeGuide 必须直接模拟的对象，而是它必须适应的人类认知约束。

如果一个人在社交中只能分配极少的注意力处理外部提示，那么 Agent 提供一段 100 字的建议，即使推理完全正确，也可能没有实际价值。

不干预

轻提示

图标/震动

短建议

几个关键词

更深层的产品设计是区分两种模式：

**Performance Mode：** 优先保证用户当前任务表现。适合演讲辅助、练习中的即时纠错等场景。

**Learning Mode：** 优先提升用户独立完成任务的能力，有意识地减少提示，让用户练习自行发现和纠正错误。

这两个目标不完全一致，不应该在产品设计中被混为一谈。

## 一、从第一性原理看，这个反驳为什么成立？

人在执行任务时，认知资源是有限的。

设用户在时刻 $t$ 的可用认知资源为 $C(t)$，当前任务占用的资源为 $L_{\text{task}}(t)$。

可供处理外部提示的剩余资源可以简化为：

$$
C_{\text{free}}(t)=C(t)-L_{\text{task}}(t)
$$

当用户正在进行高负荷社交、复杂推理或者紧张演讲时：

$$
C_{\text{free}}(t)\approx 0
$$

此时，即使 AI 能在 200 毫秒内输出一条正确建议，用户仍然需要完成：

感知提示 → 理解提示 → 判断是否采纳 → 调整当前行为。

这些操作本身就消耗认知资源。

**用户越需要 AI 的帮助，可能越没有能力接收 AI 的帮助。**

这不是单纯的推测。

2025 年关于 Just-in-Time Adaptive Interventions 的综述也明确指出了这一困难：人在最需要干预的状态下，可能恰好最不具备接收干预的能力。\[[Just-in-Time Adaptive Interventions: Where Are We Now and What Is Next?](https://pubmed.ncbi.nlm.nih.gov/40939059/?utm_source=chatgpt.com)\]

## 二、但这个反驳存在一个逻辑跳跃

你的论证可以整理为：

1. 实时任务消耗大量注意力。
2. 处理 AI 提示需要额外注意力。
3. AI 提示可能干扰当前任务。
4. 因此，只有事后复盘有效。

前三点可以成立，但第四点并不能必然推出。

因为它隐含了一个假设：

**任何实时干预都必须使用户额外执行一次有意识的认知操作。**

而这个假设不一定成立。

我们需要区分以下几种不同的干预机制。

**A. 显式语义指导**

“你现在应该先承认对方的观点，再提出自己的不同意见。”

需要阅读、理解、规划，认知成本高。

在高负荷实时社交中很可能适得其反。

---

**B. 预先学习的低维信号**

例如用户事先约定，一次短振动表示“语速过快”。

用户不需要临场解读一段新的建议，只需要识别熟悉的信号。

仍然有注意力成本，但可能比处理语言建议低得多。前提是经过训练且信号可靠。

---

**C. 直接改变任务环境**

例如在练习软件中自动突出当前推导中的可疑步骤，或在模拟对话中根据用户状态调整下一轮问题的难度。

不需要用户接收独立的指导消息。

将一部分认知处理转移到系统侧，但可能改变原本的任务体验。

---

**D. 事件驱动的事后复盘**

Agent 全程观察，不打断任务，在任务结束后针对关键事件给出分析。

几乎不引入任务执行期间的反馈处理成本，但不能直接挽回已经发生的错误。

这四者不是同一种干预。

因此，更严格的结论应该是：

**需要额外语义理解的实时指导，在高度占用注意力的任务中很难有效；但某些直接影响感知、操作或任务环境的干预，仍有可能产生净收益。**

## 三、比“提示有多短”更重要的是“提示减少了多少认知工作”

$$
\Delta L =

+
L_{\text{switch}}
+
L_{\text{adjust}}
-
L_{\text{avoided}}
$$

其中：

- $L_{\text{decode}}$：理解提示的成本。
- $L_{\text{switch}}$：切换注意力的成本。
- $L_{\text{adjust}}$：根据建议调整行为的成本。
- $L_{\text{avoided}}$：提示帮用户省去的认知工作。

这只是用于设计分析的概念模型，不代表认知负荷可以直接这样精确计量。

当 $\Delta L>0$，AI 干预增加了用户的认知负担。

# RealtimeGuide：从第一性原理推导一种 Agent Native 的实时认知辅助系统

我想先暂时抛开 RealtimeGuide 这个名字，也不预设最终一定要做实时指导、AI 教师或者事后复盘。

我们从最基本的问题开始：

**一个人正在完成某项任务。为什么他可能需要 AI 的帮助？AI 应当在什么时候、以什么方式介入？介入以后，究竟应该改善什么？**

如果这些问题能够被严格回答，产品形态应该是推导的结果，而不是起点。

我将整个推导分成四层：

LAYER 1 · HUMAN

**人的认知与行为有什么根本限制？**

认知资源、任务状态、时间约束、学习与技能

LAYER 2 · INTERVENTION

**什么条件下，外部干预会产生正收益？**

必要性、正确性、可接受性、干扰成本、反馈时机

LAYER 3 · AGENT

**怎样的智能系统才能作出这种干预决策？**

持续观察、状态估计、时机预测、干预策略、记忆

LAYER 4 · PRODUCT

**最终应该形成什么产品，如何证明它有效？**

任务场景、交互方式、实验设计、MVP、长期研究

下面逐步推导。为了保持严谨，我会区分已有研究支持的认知现象、由这些现象推出的设计要求，以及尚未得到验证的产品假设。

## 第一层：从人的任务执行开始

### 1\. 人究竟在做什么？

考虑三个场景：

- 一个人正在与陌生人交谈。
- 一个学生正在解一道数学题。
- 一个人正在向几十名听众演讲。

表面上，这三种任务完全不同。

但抽象到一定层次，它们具有共同结构：

在某个随时间变化的环境中，人持续接收信息，根据自身知识、能力和目标决定下一步行为，并观察行为的结果。

我们可以把这个过程表示为：

$$
o_t \rightarrow \text{认知处理} \rightarrow u_t
\rightarrow o_{t+1}
$$

其中：

- $o_t$：人在时刻 $t$ 接收到的信息。
- $u_t$：人在该时刻采取的行为。
- $o_{t+1}$：行为发生后得到的新观察。

这是一个循环，而不是一次性的问答。

没有 AI 时，人的自主任务执行闭环

现在我们提出第一个问题：

**这个闭环在什么情况下会表现不佳？**

### 2\. 推导人的三种基本限制

人类并不是一个可以无限计算、无限观察、无限记忆的决策系统。

至少存在三类不同的约束。

**第一类：信息约束。**

人无法观察环境中的全部状态。

在社交过程中，一个人可能只注意到对方说了什么，而没有注意到对话结构已经发生变化。

在做题过程中，学生可能没有识别出题目中的某个隐含条件。

甚至在信息已经进入感官的情况下，它也未必被正确注意和处理。

**第二类：认知计算约束。**

人能够投入当前任务的工作记忆和注意力是有限的。

一个正在组织复杂论证的人，可能难以同时监控自己的语速、表达结构和听众反馈。

**第三类：时间约束。**

即使一个人具备解决问题所需的知识和推理能力，也未必能够在任务允许的时间内完成认知处理。

例如：

- 给学生五分钟，他可以组织出正确的英语表达。
- 让他在即时对话中自然回应，他可能无法及时完成相同的处理。

因此我们得到：

$$
\boxed{
\text{具备知识}
\not\Rightarrow
\text{在当前情境下成功行动}
}
$$

这就是整个方向的第一个理论基础。

但还不能由此推出“必须使用 AI”，因为其他工具、训练方式以及环境改善也可能解决这些问题。

我们只能得到一个较弱但可靠的结论：

**在某些任务中，人可能从外部认知支持中受益。**

### 3\. System 1 和 System 2 在这里处于什么位置？

我们之前讨论过双过程理论。

从认知科学角度，Type 1 通常指能够较为自动地启动的认知加工，而 Type 2 涉及更多审慎控制、假设性推理和工作记忆参与。两者不是简单的两个独立脑区或计算模块。\[[Dual-Process Theories of Higher Cognition: Advancing the Debate](https://pubmed.ncbi.nlm.nih.gov/26172965/?utm_source=chatgpt.com)\]

这意味着，我们不能把问题简化成：

“System 1 很快，System 2 很慢，所以让 AI 帮 System 2 进行计算。”

更准确的判断是：

一个人能否成功完成即时任务，取决于其已经掌握的技能、情境识别能力、受控处理的负担，以及任务允许的时间。

特别要注意，熟练的任务表现并不意味着完全不需要审慎思考。

有时候正确的能力恰恰是识别异常，停止自动反应，转而进行分析。

所以 RealtimeGuide 不应该以“尽可能自动化人的行为”作为最终目标。

它应该关注：

**如何让有限的人类认知能力，在不同任务约束下发挥更好的作用。**

## 第二层：从外部帮助推导到干预决策

### 4\. 为什么传统的问答式 AI 可能不够？

假设用户正在完成一个持续变化的任务。

传统问答式交互往往要求：

1. 用户意识到自己需要帮助。
2. 用户决定暂停或切换当前活动。
3. 用户主动描述问题。
4. AI 理解问题并给出回答。
5. 用户重新理解任务并执行建议。

但第一步就存在问题。

**人并不总能意识到自己何时需要帮助。**

例如，学生可能不知道自己刚才的推理存在错误。

第二步同样存在问题。

当任务正在进行时，用户可能根本没有机会暂停并向 AI 描述当前状态。

因此出现一种潜在需求：

> 外部系统能否不依赖用户每次主动提问，而是根据用户授权提供的任务信息，自主判断何时可能需要帮助？

注意，推导到这里，我们需要的并不是实时建议，而只是一个能够识别辅助机会的系统。

它未必需要立即发言。

### 5\. 但外部帮助不是没有成本的

现在引入最重要的反驳：

用户正在完成高认知负荷任务，为什么还会有额外的认知资源处理 AI 的提示？

这个反驳非常有力。

假设用户正在与人交流：

AI 发现一个问题，生成一句建议，展示在用户眼前。

用户需要：

- 注意到提示；
- 理解提示内容；
- 判断建议是否正确；
- 决定如何执行；
- 在不中断对话的条件下调整行为。

即使 AI 完全正确，这个过程也可能使用户表现变差。

并且，这种成本不是简单地由提示字数决定的。

一次短振动也可能打断复杂思考；一条比较长的提示如果在任务暂停时出现，反而可能很容易处理。

因此，我们得到第二个关键结论：

$$
\boxed{
\text{AI 帮助的正确性}
\not\Rightarrow
\text{AI 帮助的有效性}
}
$$

这里已经可以初步反驳“只要 AI 能实时识别问题并及时纠错，就一定有价值”的产品假设。

### 6\. 必须建立“干预净收益”的概念

假设用户当前正在执行任务。

我们比较两种可能发生的情况：

- $a=0$：Agent 保持沉默。
- $a=1$：Agent 提供一次干预。

定义：

$$
\Delta V_t =
\mathbb E[U\mid do(a=1),h_t]
-
\mathbb E[U\mid do(a=0),h_t]
$$

这里：

- $h_t$ 是当前时刻以前的任务历史。
- $U$ 是我们关心的结果效用，可以包含任务质量、学习效果、干扰和风险。
- $do(a)$ 表示实际施加干预，而不仅仅是观察到提示与结果相关。

那么：

$$
\begin{cases}
\Delta V_t>0 & \text{干预具有正的预期净收益}\\
\Delta V_t<0 & \text{沉默具有更高的预期净收益}
\end{cases}
$$

这不是已经能够精确计算的量，而是我们的理论目标。

它有一个很重要的含义：

**Agent 的价值不等于它给出了多少条正确建议，而等于它的行为相对于不干预，改善了多少最终结果。**

例如：

一个 Agent 检测出 100 次潜在问题，给出 100 条建议，其中 90 条正确。

这不能直接说明它是好的指导系统。

如果其中 70 条都是用户能够自行解决的问题，或者大部分建议打断了重要的思考过程，那么这个系统可能具有负收益。

反过来，一个只提供 5 次干预的 Agent，可能表现得更好。

### 7\. 由此推导一个不可缺少的 Agent 动作

我们最初可能把干预动作集合定义为：

$$
A=\{\text{提醒},\text{提示},\text{纠错},\text{指导}\}
$$

但上面的结论要求我们必须加入：

$$
\boxed{\text{Silence：保持沉默}}
$$

而且沉默不是系统没有工作的状态。

Agent 仍然可以持续观察、更新判断，直到发现真正值得介入的机会。

这里已经接近心理与行为干预研究中的 Just-in-Time Adaptive Intervention（JITAI）框架。它明确将干预时点、干预选项、动态个体信息和决策规则作为独立设计要素，并强调不合适时不提供干预。\[[Just-in-Time Adaptive Interventions (JITAIs) in Mobile Health: Key Components and Design Principles for Ongoing Health Behavior Support \| Annals of Behavioral Medicine](https://academic.oup.com/abm/article/52/6/446/4733473?utm_source=chatgpt.com)\]

但这是一个已有的研究框架，不应直接当成 RealtimeGuide 自己发明的新理论。

我们的机会是把这套干预决策思想进一步应用到 AI 教育与复杂实时任务中。

### 8\. 进一步推导：为什么“实时”不是一个充分条件？

我们还没有回答你之前的反驳。

假设 Agent 在时刻 $t$ 发现了一个问题。

这个问题可能有一个有效干预期限 $D_t$。超过期限，即使建议正确，也无法改变已经发生的行为。

设一次完整的干预包括：

$$
T_{\text{total}}=
T_{\text{sense}}+
T_{\text{infer}}+
T_{\text{deliver}}+
T_{\text{human}}
$$

前三项分别是数据获取、AI 推理和提示送达耗时。

最后一项 $T_{\text{human}}$，是用户理解和执行建议的耗时。

如果：

$$
T_{\text{total}}>D_t
$$

那么，这次实时指导就无法在当前决策窗口内发挥预期作用。

但即使满足：

$$
T_{\text{total}}\le D_t
$$

也不能保证干预有益，因为它仍然可能打断用户思考，或者让用户采纳错误建议。

所以，实时指导至少需要同时满足三个条件：

1. **Timeliness**：能够赶上有效的行为调整窗口。
2. **Receptivity**：用户此时能够接收、理解并执行提示。
3. **Net Benefit**：干预带来的收益超过干扰和错误风险。

三个条件中任何一个不成立，沉默或延迟指导都可能更好。

已有中断管理研究也发现，在任务不同阶段提供通知具有不同的认知成本，子任务边界是值得关注的干预时机。\[[Understanding changes in mental workload during execution of goal-directed tasks and its application for interruption management](https://doi.org/10.1145/1314683.1314689?utm_source=chatgpt.com)\]

我们因此得到一个比“低延迟”更重要的技术指标：

$$
\boxed{\text{Effective Intervention Window}}
$$

即有效干预窗口。

一个 AI 系统能在 100 毫秒内输出建议，并不一定比一个在正确时间提供建议的系统更有效。

## 第三层：究竟应该做实时指导，还是事后复盘？

### 9\. 必须拆开两个经常被混淆的维度

我们之前一直在讨论“实时”与“事后”。

但实际上存在两个独立问题：

**问题 A：AI 在什么时候理解任务？**

- 实时观察与推理。
- 任务结束后回放和分析。

**问题 B：AI 在什么时候向用户提供帮助？**

- 任务执行期间。
- 任务间隙。
- 任务结束后。

因此，我们至少存在四种基本方案：

|  | 实时给予反馈 | 事后给予反馈 |
|--------|--------|--------|
| **实时分析任务** | 实时指导 Agent | 实时事件理解 + 延迟指导 |
| **事后分析任务** | 不可用于已经结束的任务 | 录像/记录分析与复盘 |

这张表引出了一个必须正视的问题：

**如果我们的产品最终只提供事后复盘，为什么还需要实时推理？**

这是对 RealtimeGuide 非常有力的反驳。

如果任务全过程能够完整记录，且用户在结束前不需要系统采取任何行动，那么实时推理可能完全没有必要。

我们可以录制整个过程，然后使用更强的模型进行离线分析。

这种方式甚至可能更便宜、更准确，并且不受实时计算资源限制。

所以不能因为产品叫 RealtimeGuide，就预设所有推理必须实时运行。

### 10\. 那么什么时候真正需要实时推理？

只有在实时状态理解能够改变任务进行中的某件事情时，其必要性才真正出现。

例如：

**情境 A：即时行为调整**

演讲者已经明显偏离预定时间，Agent 在仍有机会调整演讲结构时发出短提示。

此时实时推理可能有价值。

**情境 B：自适应训练**

学生正在与模拟的 AI 面试官交互。

Agent 根据学生刚才的表现，实时调整下一次提问的难度和方式。

注意，这里不是向学生提供外部提示，而是改变训练环境本身。

**情境 C：机会性指导**

学生结束一道题的中间步骤，系统识别这是一个相对合适的反馈窗口，于是给出短提示。

**情境 D：完全事后复盘**

演讲结束之后，系统指出结构问题、语速变化和重要事件。

如果无需在演讲中调整任何行为，那么实时推理可能没有明显优势。

由此得到一个非常重要的架构原则：

> **实时推理应该由实时决策的必要性决定，而不应成为系统的先验约束。**

这也是我们推导至此对原始 RealtimeGuide 概念作出的第一次实质性修正。

### 11\. 将干预扩展为三个时间尺度

我认为一种更合理的系统应该允许 Agent 在多个时间尺度上工作。

**Level 1 · 即时干预** 任务进行中

对能够及时修正、风险较低且用户容易理解的问题进行最小必要干预。

例如：演讲时间预警、预先约定的简短信号。

**Level 2 · 机会性干预** 任务自然间隙

等待注意力负担较低的阶段，再提供局部反馈或指导。

例如：完成一个解题步骤后，提示检查某个条件。

**Level 3 · 事后复盘** 任务结束后

重建完整过程，分析决策、错误、替代策略与后续训练需求。

例如：复盘一次小组讨论中错失的回应机会。

这三个层次并不是相互排斥的产品功能。

它们是同一类干预决策的不同选项。

换句话说，RealtimeGuide 不是必须在三个模式之间让用户手动选择。

更理想的 Agent 应该能够根据任务和用户状态，自动决定具体反馈应该出现在哪一个时间尺度。

## 第四层：重新引入教育目标

到目前为止，我们推导出来的是一种通用的认知辅助系统。

它可以帮助人们演讲、解题、社交，也可以帮助人们操作复杂软件。

但它为什么是一个教育产品？

这需要引入另一个问题。

### 12\. 帮助用户完成任务，与帮助用户学习，不是同一个目标

假设用户正在解决一道数学题。

有两种策略：

- 策略 A：发现用户卡住，立即告诉他下一步。
- 策略 B：暂不介入，允许他继续探索，在适当时机提供少量帮助，之后复盘。

策略 A 可能提高当前任务完成率。

策略 B 可能更有利于训练用户的独立解题能力。

但 B 并不一定总是更好；如果学生缺乏必要的先修知识，完全不提供帮助也可能导致无效尝试。

所以需要明确区分两个目标函数。

**目标一：当前任务表现**

$$
J_P = \mathbb E[\text{当前任务的综合表现}]
$$

**目标二：长期自主能力**

$$
J_L = \mathbb E[\text{未来无辅助任务的表现}]
$$

对于一般生产力 Agent，我们往往更关心 $J_P$。

对于教育 Agent，我们必须认真考虑 $J_L$。

2025 年发表于《PNAS》的一项高中数学现场实验提供了直接的警示：未经充分约束的 GPT 辅助提高了练习阶段的成绩，但在随后移除 AI 的独立考试中，相关学生群体反而表现更差；采用教学保护措施的版本基本消除了这一负面影响，但也没有观察到明确的独立考试正向收益。\[[Generative AI without guardrails can harm learning: Evidence from high school mathematics](https://doi.org/10.1073/pnas.2422633122?utm_source=chatgpt.com)\]

因此：

$$
J_P\uparrow
\not\Rightarrow
J_L\uparrow
$$

这对于 RealtimeGuide 意味着什么？

**一个在任务中不断纠正用户、让用户看起来表现完美的 Agent，可能并不是一个优秀的教育 Agent。**

### 13\. 于是导出两种不同的优化策略

|  | Performance Mode | Learning Mode |
|--------|--------|--------|
| 主要目标 | 改善当前任务表现 | 提升长期自主能力 |
| 遇到错误 | 倾向于及时阻止有代价的错误 | 可能允许安全的错误发生 |
| 反馈形式 | 简洁、可执行 | 启发、解释、复盘 |
| 对沉默的理解 | 没有必要干预 | 可能是有意保留学习机会 |
| 评价指标 | 当前成功率、效率、可靠性 | 延迟保持、独立完成、跨情境迁移 |

但是，我不建议最终只提供一个简单的二选一开关。

更合理的是，在用户目标明确的前提下，让系统对两种目标进行联合优化：

$$
J=
J_P+\lambda J_L-C_{\text{intervention}}
$$

其中 $\lambda$ 表示长期学习收益相对于当前表现的权重。

对于一次正式演讲，当前表现可能更重要。

对于一次演讲训练，长期技能提升可能更重要。

这里不能靠模型自己猜测用户真正想要什么。用户必须能够设定和调整目标。

### 14\. 这也改变了 System 1 的定位

我们现在可以重新审视最初的 System 1 想法。

如果目标是让学生在真实情境中形成快速、可靠的反应能力，那么 RealtimeGuide 可能需要经历一个过程：

**初期**

提供充分的解释、提示和演练

**中期**

减少提示，让用户自主识别和纠正

**后期：独立迁移**

在不同于训练环境的情境中，不依赖 AI 也能正确识别问题、选择行动，并在必要时审慎思考。

这涉及技能学习中的自动化、反馈逐步撤除，以及训练与真实情境之间的迁移。

但要严谨地区分：

- 训练中表现更快，不必然意味着形成了自动化技能。
- 对提示的反应越来越熟练，不必然意味着真实任务能力提高。
- AI 能够判断何时指导，也不意味着它能准确观察用户的内部认知过程。

因此，System 1 更适合作为解释产品设计问题的认知理论之一，而不是直接成为产品宣称能够优化的单一可测量变量。

## 第五层：从理论推出 Agent 的完整决策模型

### 15\. 用户状态不是直接可见的

到这里，我们知道 Agent 需要判断：

用户是否需要帮助？什么时候可以接受帮助？哪种帮助更合适？

但它实际上无法直接读取用户的认知状态。

例如，学生突然停止写题。

这可能意味着：

- 他不会做。
- 他正在进行复杂的心算。
- 他发现了一个错误，正在自己检查。
- 他走神了。
- 他只是暂时休息。

相同的外部现象对应不同的内部状态。

因此，如果我们要建立一个形式化模型，更合理的是将其视为**部分可观察的序贯决策问题（POMDP）**。

设真实状态为：

$$
s_t=(e_t,g_t,k_t,w_t,\tau_t)
$$

分别表示：

| 状态 | 含义 |
|--------|--------|
| $e_t$ | 外部环境及当前任务进度 |
| $g_t$ | 用户目标 |
| $k_t$ | 相关知识、技能与能力状态 |
| $w_t$ | 当前认知负荷或可接受性状态 |
| $\tau_t$ | 时间约束与任务阶段 |

Agent 只能获得屏幕、语音、操作行为等观测 $o_t$。

所以系统维护的不是确定的 $s_t$，而是关于状态的概率性估计：

$$
b_t(s)=P(s_t=s\mid o_{1:t},a_{1:t-1})
$$

即 belief state。

需要强调，POMDP 是一种有用的建模选择，不代表必须在黑客松里训练完整的强化学习模型。

一个显式状态机加少量统计判断、规则验证和 LLM 推理，也可以近似实现这个思想。

### 16\. Agent 应该有哪些动作？

原始的指导 Agent 可能只有：

$$
A=\{\text{给出建议}\}
$$

但经过上面的推导，我们至少得到：

$$
A=
\begin{cases}
a_0:\text{保持沉默}\\
a_1:\text{即时低负荷提示}\\
a_2:\text{即时简短指导}\\
a_3:\text{延迟到任务边界}\\
a_4:\text{记录并事后复盘}\\
a_5:\text{调整训练环境}
\end{cases}
$$

其中 $a_5$ 很值得注意。

因为 Agent 不一定需要直接指导用户。

例如在模拟面试中，系统可以改变面试官的提问策略，在用户表现不佳时适当降低难度，在用户表现较好时增加挑战。

这样，Agent 通过改变训练环境来促进学习，而不是通过在用户耳边说话来干预。

这可能是绕开实时认知干扰的一条重要路径。

### 17\. 最终的干预策略

我们定义一个策略：

$$
\pi(a\mid b_t,g)
$$

它根据当前状态估计和用户目标，决定采取什么动作。

RealtimeGuide 干预决策流程

检测到一个值得关注的任务事件

事件判断是否有足够证据？

证据不足

不立即纠偏

继续观察、低置信度标记或稍后询问

证据充分

评估干预时机

剩余时间、认知负担、任务代价

估计不同动作的净收益

即时提示 / 延迟提示 / 复盘 / 沉默

选择最合适的动作

记录结果，并更新对用户状态的估计

这个决策模型也是我们区别于简单 AI Tutor 的核心。

它不是在收到提问后生成回答，而是在观察任务、识别候选事件、评估可采取的动作，再决定是否干预。

### 18\. 但这里仍然存在一个因果推断难题

Agent 很容易判断一次建议之后用户是否成功。

但这不能证明这条建议造成了成功。

因为即使没有这条建议，用户也可能自行完成任务。

形式上，我们想知道：

$$
U(\text{提示})-U(\text{不提示})
$$

但在同一个任务、同一个时间点，无法同时观察这两种结果。

这是典型的反事实问题。

这意味着只靠“收集用户接受提示后的成功率”，无法可靠训练出最优干预策略。

真正要研究干预效果，就需要合理的随机化对照。

相关研究已经发展出 Micro-Randomized Trial（微随机试验），通过在多个符合条件的决策时点随机分配不同干预选项，估计干预对近端结果的因果影响。\[[The microrandomized trial for developing digital interventions: Experimental design and data analysis considerations](https://pubmed.ncbi.nlm.nih.gov/35025583/?utm_source=chatgpt.com)\]

这个研究方法非常适合 RealtimeGuide，但实际应用必须先确保实验场景安全、可控，并且能够获得用户同意。

## 第六层：把理论映射到三个真实场景

经过前面的推导，我们不应该直接问：

“社交、做题、演讲，哪一个最适合 AI？”

应该先问：

**这些任务中的哪些状态是可观察的？哪些干预具有可验证的价值？**

| 维度 | 社交 | 做题 | 演讲 |
|--------|--------|--------|--------|
| 可观察输入 | 语音、对话轮次、内容 | 公式、步骤、操作行为 | 语音、幻灯片、时间 |
| 可判断的事件 | 话题切换、未回应的问题 | 可验证的推导错误、步骤完成 | 超时、语速变化、内容遗漏 |
| 实时反应窗口 | 通常较短且不稳定 | 依解题阶段变化 | 相对容易识别过渡阶段 |
| 实时指导风险 | 较高 | 中等，可能干扰思考 | 中等，可能影响表达 |
| 复盘价值 | 高 | 高 | 高 |
| 自动化评估难度 | 较高 | 结构化题目较低 | 部分指标较低 |

下面分别推导。

### 19\. 社交场景

社交有一个明显的特点：用户的行为与他人的回应高度耦合。

用户正在说话时，如果 Agent 弹出一条复杂建议，用户可能根本无法处理。

因此显式语言提示的可用性有限。

但我们还存在三种有价值的可能：

- 低维、预先训练过的提示信号。
- 在自然话题间隙提供简短建议。
- 在对话结束后，基于具体时间点进行事件复盘和情境重演。

这里的难点不只是 AI 能否理解对话。

更难的是：什么才算“正确的社交行为”？

例如，用户没有积极回应对方，并不一定是错误；可能是用户有意保持边界。

因此，系统不能擅自把某种社交规范当作客观正确答案。

它必须先知道用户想要达成什么目标，并允许用户否决系统对行为的评价。

如果涉及真实第三方对话，还必须解决知情同意、录音和数据保留等隐私问题。

**结论：社交是很有潜力的长期应用，但直接把它作为第一版通用实时纠偏产品，技术与评估风险都较高。**

### 20\. 做题场景

做题有一个天然优势：部分错误可以形式化验证。

例如学生解方程：

$$
x^2=9
$$

随后写出：

$$
x=3
$$

系统能够判断答案遗漏了另一种可能：

$$
x\in\{-3,3\}
$$

但接下来出现一个更有意思的问题：

**AI 是否应该立即提醒？**

不一定。

如果学生正在检查自己刚才的步骤，马上提示可能剥夺一次自主纠错机会。

如果学生已经进行很多后续推导，错误开始不断累积，适当干预可能更有价值。

如果学生是在考试环境中，则还需要考虑是否允许外部辅助。

因此，真正的 Agent Native 不是“检测到错误立即弹窗”，而是：

1. 判断错误是否确定。
2. 判断错误是否正在影响后续工作。
3. 识别用户是否可能自行纠正。
4. 根据学习目标决定是否介入。
5. 如果没有介入，仍然能够在复盘中解释这个事件。

这类场景特别适合研究我们之前定义的干预策略，因为判断结果相对容易验证。

### 21\. 演讲场景

演讲有一个非常重要的优势：

**它存在相对明确的任务目标、时间预算和可观察进度。**

例如用户准备演讲三分钟，计划介绍五个内容节点。

演讲进行到后半段时，系统发现某些关键内容还没有覆盖。

这就可以构造一个比较有依据的干预判断：

- 剩余时间是否足够？
- 是否有必要跳过次要内容？
- 当前是否接近幻灯片切换？
- 用户能否接受一个简短的时间提醒？

和社交相比，演讲中的某些干预可以建立在比较可靠的外部状态上，而不必猜测用户内心正在想什么。

但对“演讲质量”的主观判断仍需谨慎。

例如，语速快不必然等于表达差；暂停也不必然代表紧张。

**结论：演讲适合验证低延迟干预和事件驱动复盘，但做题更适合验证教学干预是否真正改善学习。**

## 第七层：导出 RealtimeGuide 的系统架构

### 22\. 我们究竟需要怎样的 Agent？

如果严格遵循上面的推导，系统不应该是一个始终接收所有视频帧、不断调用 LLM、持续输出建议的程序。

那样既浪费计算资源，也不符合我们提出的干预原则。

我会将它划分成六个逻辑模块。

**1\. Perception Layer**

获取授权的语音、屏幕、文档、操作事件等输入

**2\. Event Detection**

识别有意义的状态变化，形成带时间戳的候选事件

**3\. State Estimation &amp; Reasoning**

维护任务状态，结合历史和领域规则推断问题与机会

**4\. Intervention Policy**

考虑证据置信度、干扰成本、时间窗口和用户目标，决定是否、何时、如何干预

**5A. Delivery**

低干扰提示、即时指导、任务边界提示

**5B. Review**

事件复盘、证据回放、针对性训练

**6\. Evaluation &amp; Adaptation**

记录用户响应、后续行为和实际效果，更新策略

其中最关键的是第四层。

前三层负责弄清楚发生了什么。

第四层负责决定是否值得采取行动。

后两层负责提供干预，并验证其实际结果。

### 23\. 为什么这应该是 Agent Native，而不只是一个 AI 功能？

现在我们终于可以回答这个问题。

如果只是传统 AI 功能：

用户按下按钮 → 调用模型 → 返回建议。

如果是我们推导的 Agent：

系统长期维护任务状态 → 自主识别决策机会 → 在多个动作中作出选择 → 观察结果 → 调整后续策略。

这种区别不是有没有聊天框，也不是有没有多 Agent 框架。

而是系统是否对持续的任务过程负责。

但这里还需要避免另一个概念陷阱：

**Agent Native 并不意味着每一步都必须由大模型完成。**

例如：

- 实时语速统计可以由信号处理和语音识别完成。
- 数学表达式验证可以由符号计算完成。
- 时间窗口管理可以由普通程序完成。
- 复杂语义分析和复盘可以由推理模型完成。

如果使用一个庞大的 LLM 来重复执行简单、确定性的判断，反而不符合工程上的最优设计。

### 24\. 具体实现应该是快慢两层

我会把计算系统进一步分成两条路径：

| 快路径 | 慢路径 |
|--------|--------|
| 接收事件流 | 深入分析历史事件 |
| 低成本更新任务状态 | 进行复杂推理 |
| 检测明确异常 | 诊断错误原因 |
| 判断紧急提示是否可用 | 生成复盘和训练建议 |
| 严格控制延迟 | 允许更长计算时间 |

关键是快路径不能无限依赖慢路径。

如果某个提示的有效窗口已经消失，就应直接丢弃，而不是在用户完成操作后才显示一个过时建议。

另外，系统应该优先存储与任务有关的结构化事件，而不是默认永久保存完整音视频。

例如一条事件可以包含：

```json
{
  "timestamp_ms": 82500,
  "scenario": "presentation",
  "event": "time_budget_risk",
  "evidence": {
    "time_remaining_sec": 38,
    "sections_remaining": 2
  },
  "confidence": 0.94,
  "intervention": "deferred",
  "reason": "user_is_mid_sentence"
}
```

这是示例数据，不是真实模型推理结果。

事件记录的意义在于把系统决策与具体证据绑定，使之后能够追溯：

- AI 发现了什么？
- 为什么当时没有提示？
- 为什么选择延迟？
- 用户之后发生了什么？

没有这样的可追溯性，我们就很难判断系统究竟是有效，还是只是看起来聪明。

## 第八层：怎样证明这个产品不是伪需求？

### 25\. 我们需要验证的不是一个假设，而是一组假设

目前 RealtimeGuide 至少隐含以下五个假设。

| 假设 | 需要验证的问题 |
|--------|--------|
| H1：状态可观测 | 系统能否从外部行为可靠地识别重要任务事件？ |
| H2：机会可预测 | 能否识别用户更容易接受指导的时机？ |
| H3：实时干预有价值 | 在某些条件下，实时干预是否优于沉默？ |
| H4：自适应策略有价值 | 自动选择干预时机是否优于固定策略？ |
| H5：学习能够迁移 | 用户在没有 AI 时是否真正进步？ |

这里任何一个假设不成立，都可能迫使产品改变形态。

例如：

- H1 不成立：需要缩小到可验证的任务。
- H2 不成立：应减少主动提示。
- H3 不成立：更应关注记录与复盘。
- H4 不成立：复杂策略可能不值得开发。
- H5 不成立：产品可能更适合定位为生产力辅助，而不是教育。

### 26\. 最关键的对照实验

至少需要比较四种条件：

A · Control

**无 AI 指导**

作为正常任务表现的基线。

B · Delayed

**仅事后复盘**

观察与记录任务，但不在过程中提示。

C · Immediate

**固定规则即时指导**

满足预设条件就立即提示。

D · Adaptive

**自适应指导**

动态选择即时、延迟、复盘或沉默。

尤其要注意，不能只比较任务结束时的主观满意度。

我们应该观察两个阶段。

**阶段一：有 AI 时的任务表现。**

测量任务完成质量、错误率、干扰次数、实际采纳率，以及用户报告的认知负担。

**阶段二：没有 AI 时的独立表现。**

测量用户是否能够独立完成类似任务，以及在陌生任务、延迟测试中是否保持能力。

如果 D 组当前表现更好，但没有产生任何长期能力提升，那么它可能是一个有效的实时辅助工具，却未必是有效的教育工具。

如果 B 组独立能力提升更明显，则说明事后复盘可能更适合该类任务的学习目标。

如果 C 和 D 都不能超过 B，我们就应该严肃考虑取消实时提示功能。

反馈时机研究本身也没有给出一个普遍适用的最佳方案。一项汇总 53 项研究的经典元分析发现，即时和延迟反馈的效果取决于任务类型与研究环境。\[[Timing of Feedback and Verbal Learning - James A. Kulik, Chen-Lin C. Kulik, 1988](https://journals.sagepub.com/doi/10.3102/00346543058001079?utm_source=chatgpt.com)\]

所以真正值得研究的是条件，而不是宣布某种反馈形式始终优越。

## 第九层：最终能够形成怎样的产品？

### 27\. 我现在会把 RealtimeGuide 定义为一个干预决策系统

经过完整推导，原始定义：

> 一个持续监测用户、实时推理并给予指导的 AI Agent。

我认为还不够严谨。

它隐含了一个不必要的偏见：实时给予指导本身就是好的。

我更倾向于将其定义为：

> **RealtimeGuide 是一种面向持续性任务的人机协同 Agent。它通过感知和理解用户当前的任务状态，结合用户目标、行为上下文和反馈可接受性，动态决定是否、何时以及如何提供认知支持，并通过后续行为和任务结果评估干预效果。**

如果专注于教育，可以进一步补充：

> 系统不仅优化当前任务表现，还应促进用户在无辅助条件下的自主能力与跨情境迁移。

这样，我们不再把系统价值绑定在实时弹出建议上。

真正的产品核心是：

**Intervention Policy：智能干预策略。**

我会让用户拥有一个统一的任务会话，而不是三个彼此无关的 Chatbot。

- 演讲

以上是交互概念示意，不是真实的持续监测系统。

我认为一个重要的 UI 设计原则是：**用户不需要始终看到 Agent 正在思考什么。**

任务结束后，用户才可以查看完整的事件时间线、干预决策和复盘内容。

## 第十层：如果把它作为本次苏客松项目

我们现在终于可以讨论如何落地，而不是从一开始就用黑客松约束扭曲理论。

### 29\. MVP 不需要证明全部理论

在约 41 小时的开发窗口中，不可能严谨证明长期学习迁移，也难以训练出可靠的通用认知负荷估计模型。

因此，我不会尝试一开始完成整个系统。

我建议第一版仅验证三个能力：

1. **Continuous Understanding**：能够持续感知任务、维护上下文并检测可验证事件。
2. **Adaptive Intervention**：能够依据任务阶段，选择即时指导、延迟指导或沉默。
3. **Evidence-based Review**：能够在结束后展示关键事件、证据及针对性反馈。

最好的核心展示场景是**演讲**，因为它更容易让评委直观地看见持续观察、时机决策和实时提示的差异。

做题可以作为第二个适配场景，用于证明系统具有超出演讲的通用性。

社交模拟则保留为后续扩展方向，因为其行为评价相对主观，实时提示也更容易干扰对话。

### 30\. 什么才是真正有竞争力的 Demo？

不要只展示：

“AI 发现演讲者语速快，于是显示请放慢语速。”

这只是一个反馈功能。

我更希望展示这样的完整过程：

1. **用户开始演讲。** 系统接入语音流和演示文稿，知道预期内容与时间限制。
2. **系统发现事件。** 用户已经消耗大部分时间，但仍有重要内容没有覆盖。
3. **Agent 判断不立即介入。** 当前用户正在连续表达，提示可能打断论证。
4. **系统识别到合适时机。** 用户切换幻灯片，于是出现一个简短的时间建议。
5. **用户调整演讲。** 系统观察之后的进度变化。
6. **任务结束后复盘。** 显示完整事件时间线、何时提示、何时保持沉默，以及原因和对应证据。

这个 Demo 的重点不是 AI 模型说了多聪明的话。

而是它展示了一项能够被观察和验证的能力：

**Agent 不只知道发生了什么，还能够决定何时采取行动。**

如果有时间进一步测试，可以让同一个用户在无辅助、固定提示和自适应提示三种条件下完成难度相近的任务，作为探索性对比。

但小规模现场体验只能证明交互流程与初步可用性，不能证明长期教育效果或因果优势。

## 最后：从整个推导中得到的核心结论

我们现在可以把推导压缩成一条逻辑链：

但是，这里存在一个我认为非常值得继续研究的关键问题：

**我们实际上还没有证明，一个 Agent 能可靠估计“此刻干预比不干预更好”。**

它可能知道用户犯了什么错误，却不知道用户是否已经意识到错误。

它可能知道一个提示完全正确，却不知道用户是否有能力在此时处理提示。

它可能知道用户因为提示而改善了当前表现，却不知道这种改善是否损害了长期学习。

因此，RealtimeGuide 真正困难的地方，不在于接入屏幕、麦克风，甚至也不在于实时调用大模型。

而在于建立一个可靠的**人机干预决策机制**。

我会把这个项目最值得探索的研究问题最终表述为：

> **Can an AI agent learn when, whether, and how to intervene in an ongoing human task to improve performance and long-term learning, without imposing excessive cognitive load?**
>
> AI Agent 能否学会在人的持续任务中，判断何时、是否以及如何介入，从而改善当前表现与长期学习，同时避免施加过量的认知负担？

这是一个可提出假设、可构建系统、可进行实验、也允许得出否定结果的研究问题。

而从产品角度，最有意思的转变是：

**我们不是在做一个随时给人答案的 AI，而是在研究一种知道什么时候不应该给人答案的 AI。**

这才是我认为 RealtimeGuide 能从普通 AI Tutor、屏幕助手、语音助手中真正分化出来的地方。

# RealtimeGuide - Agent Native 实时认知辅助产品设计

Product Concept v0.1 · Jev-like System 1 × Pi Agent Harness

我建议把 RealtimeGuide 设计成一个**以实时任务为中心、由 AI 自主决定干预时机和方式的认知辅助平台**。

它不应该只是一个具有屏幕识别能力的 Chatbot，也不应该是不断弹出建议的 AI 教师。

我设想的最终产品由三个部分构成：

**1\. Live Companion - 实时伴随层**

在用户演讲、解题、交流时安静运行，持续理解任务。仅在合适的时间，用最小必要的交互提供帮助。

---

**2\. Agent Runtime - 智能决策层**

Jev-like System 1 负责高频、边界清晰的决策；Pi Agent 负责复杂分析、工具调用、教学策略和上下文管理。

---

**3\. Reflection Studio - 复盘与训练层**

将持续观察转化为可追溯的事件时间线、行为分析、交互式重演和下次训练计划。

这样既保留了“Realtime”的价值，又解决了之前最关键的反驳：**用户没有认知资源处理建议时，系统应当能够选择沉默，把指导延后。**

## 一、先明确 Jev 与 Pi 的技术分工

我核对了两个项目的当前实现。

**[Jev / TypeSafe System One](https://docs.typesafe.ai/introduction?utm_source=chatgpt.com)** 不是普通的生成式 LLM。它接受一份状态和若干类型化问题，返回 Choice、Score 或 Noul（是/否概率）等结构化结果。官方将其定位为快速决策模型，而不是文本生成模型。\[[Introduction](https://docs.typesafe.ai/introduction?utm_source=chatgpt.com)\]

**[Pi Agent](https://github.com/earendil-works/pi?utm_source=chatgpt.com)** 则是可扩展的 Agent Harness，具有模型调用、工具执行、会话管理、上下文构建、SDK 和扩展机制。其核心 Agent Loop 是生成式模型驱动的，并不天然适合承担每个视频帧或每个音频块的实时判断。\[[GitHub - earendil-works/pi: AI agent toolkit: unified LLM API, agent loop, TUI, coding agent CLI](https://github.com/badlogic/pi-mono?utm_source=chatgpt.com); [SDK · Documentation](https://pi.dev/docs/latest/sdk?utm_source=chatgpt.com); [How Pi Works · Documentation](https://pi.dev/docs/latest/how-pi-works?utm_source=chatgpt.com)\]

所以我不建议让 Jev 和 Pi 互相调用、组成一个串行的“双模型思考链”。

建议架构：双速决策 + 独立执行控制

**连续输入与事件处理**

语音 / 屏幕 / 笔迹 / 操作记录 / 任务目标

**System 1**

Jev-like 决策模型

状态分类、风险判断、时机判断、候选动作选择

低延迟、频繁调用

**System 2**

Pi + 推理 LLM

复杂诊断、工具调用、教学规划、反事实分析

异步、按需调用

**Intervention Controller**

权限、时间有效性、冷却、冲突仲裁、是否真正执行

这里的重点是：**System 1 和 System 2 都不能直接、无限制地控制用户界面。**

它们提供判断和建议，最终的干预权限属于一个独立的、可审计的 Controller。

这也让未来替换 Jev、使用本地决策模型，或者换掉 Pi Harness 成为可能，而不需要推翻整个产品。

## 四、我建议的四个产品核心模块

### A. Live HUD：近乎隐形的伴随界面

不同任务需要不同的提示介质，但应遵循相同的设计原则。

**Silent**

系统后台观察，用户无须处理任何消息。

**Minimal Cue**

利用用户预先理解的信号，传达单一信息。

**Short Guidance**

检查两种符号

在认知负担较低的时机提供一句简短建议。

**Deep Review**

任务完成后再提供完整分析与训练建议。

### B. Reflection Studio：把“复盘”做成核心产品

这里我不建议使用传统 LLM 的长篇总结报告。

复盘应该基于有证据支撑的事件，而不是生成一段泛泛的评价。

每个事件都有独立详情页：

| 字段 | 内容 |
|--------|--------|
| 发生了什么 | 时间戳、录音片段、屏幕或操作证据 |
| Agent 当时看到了什么 | 已知上下文与证据置信程度 |
| Agent 为什么这样处理 | 触发条件、选择的动作及原因 |
| 用户做了什么 | 干预后的可观察行为 |
| 有哪些替代方案 | 由 Pi Agent 进行较深入的分析 |
| 能否再练一次 | 将事件重新构造成训练场景 |

其中最有潜力的功能是 **Replay &amp; Retry**。

例如，演讲者在第 1 分 35 秒遗漏了一个论证环节，系统不只是指出错误，而是能够从那个上下文重新启动一轮模拟，让用户再尝试一次。

这比纯文本复盘更接近真实的技能训练。

### C. Guide Studio：可配置的场景插件

产品需要一个统一的场景定义，而不是为演讲、解题、社交分别编写完全不同的 AI 应用。

```typescript
interface GuidePack {
  id: string;
  name: string;

  sensors: SensorSpec[];
  eventDetectors: EventDetector[];
  stateSchema: Schema;
```

其中每个 GuidePack 定义五件事：观察什么、什么算事件、哪些判断需要 AI、允许采取什么动作，以及如何验证结果。

例如：

| GuidePack | 感知重点 | 领域工具 |
|--------|--------|--------|
| Presentation | 语音、时间、幻灯片内容 | 时间统计、内容覆盖检测 |
| Math Tutor | 公式、步骤、提交事件 | 符号计算、步骤验证 |

这样的可扩展性，比简单宣布“我们支持所有教育场景”更有技术说服力。

### D. User Model：持续适应学习者

这里需要小心设计。

Agent 不应该未经证实地给用户贴上“注意力不足”“社交能力差”等标签。

更适合保存的是可观察的、任务相关的学习记录，例如：

- 用户在哪类数学步骤上经常遗漏条件；
- 用户曾拒绝哪些类型的实时提示；
- 用户是否经常在某类任务边界自行纠正错误；
- 对同类提示，用户的采纳情况是否发生变化；
- 在撤除 AI 后，是否仍能独立完成任务。

这使 RealtimeGuide 能逐渐调整策略。

例如某个学生已经能自主纠正符号遗漏，那么系统应该降低这类错误的提示频率，而不是永远把同一件事情提醒给他。

## 五、System 1 决策模型的具体设计

这是整个系统中最值得投入技术研究的部分。

### 1\. 不让 Jev 直接完成复杂综合判断

TypeSafe 官方明确建议将复杂判断拆成边界清晰的原子问题，再由程序组合。其模型文档也指出，Jev 1.13 在精确数学计算、数值比较以及多层间接推理上存在局限。\[[Introduction](https://docs.typesafe.ai/introduction?utm_source=chatgpt.com); [Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13?utm_source=chatgpt.com)\]

因此，不能简单地给 Jev 一段用户行为，直接询问：

“现在要不要提醒用户？”

这个问题过于宽泛。

我建议拆成几个可独立评估的信号：

| 决策信号 | 适合的处理方式 |
|--------|--------|
| 是否存在明显的语义错误候选 | Jev Noul / 领域验证器 |
| 当前事件的紧迫程度 | Jev Score |
| 用户是否处于容易打断的阶段 | Jev 分类 + 确定性任务事件 |
| 该错误是否已被用户自行纠正 | 事件状态机 / 验证器 |
| 是否超过时间预算 | 确定性程序 |
| 是否应该请求复杂推理 | Jev Choice / 规则 |
| 最终是否允许弹窗 | Intervention Controller |

注意，System 1 在这里指软件中的快速决策层，**不等于它准确模拟了人类心理学中的 System 1**。

### 2\. 一个具体的决策请求

以下是基于 TypeSafe 当前接口概念设计的简化请求，非实际运行输出。

```json

  "state": {
    "scenario": "presentation",
    "event": "topic_coverage_risk",
    "speaker_state": "mid_sentence",
    "remaining_seconds": 48,
    "uncovered_points": 2
  },
  "questions": {
    "risk": {
      "type": "score",
      "instructions": "Assess the urgency of the coverage risk.",
      "criteria": [
        "No meaningful risk",
        "Low risk",

        "Critical risk"
```

实际实现时，先由确定性代码计算剩余时间与内容节点数量，再交给 Jev 判断语义相关的不确定因素。

Jev 的评分和概率不能直接视为干预因果收益，也不能在未经验证时直接解释为用户心理状态的真实概率。

### 3\. Intervention Policy 必须独立存在

模型输出以后，由程序进行最后一道仲裁。

```typescript
function decideIntervention(ctx: Context): Action {
  if (!ctx.userAllowsGuidance) return "SILENT";
  if (ctx.eventExpired) return "LOG_ONLY";
  if (ctx.inCooldown) return "DEFER";

  if (ctx.evidenceInsufficient) {
    return "OBSERVE";
  }

  if (ctx.taskPhase === "high_load") {
    return "DEFER";
  }

  if (ctx.expectedDisruption > ctx.expectedBenefit) {
    return "LOG_ONLY";
  }

  return ctx.goal === "learning"
    ? "MINIMAL_HINT"
    : "SHORT_GUIDANCE";
}
```

这段代码只是策略示意。`expectedDisruption` 和 `expectedBenefit` 目前不能直接由 Jev 可靠地产生，需要以规则、用户反馈和后续实验逐步估计。

模型负责评估状态，程序负责执行明确的产品规则。

**不要因为 Jev 返回了一个高置信度答案，就自动对用户采取行动。**

独立评估研究已发现，System 1 决策模型在不同任务上的可靠性差异明显；孤立问题的准确率也不能直接代表整个 Agent 工作流的成功率。\[[Evaluating and Benchmarking the System One Model Jev](https://arxiv.org/abs/2609.37647?utm_source=chatgpt.com); [JevAgentHarness: Benchmarking, Deploying and Training Decision Models That Share Control with LLMs](https://arxiv.org/abs/2610.21412?utm_source=chatgpt.com)\]

## 七、性能、成本与隐私方面的设计原则

性能架构

我建议采用事件驱动，而不是把视频每一帧都发送给 Jev 或 LLM：

```text
Continuous Signals
       ↓
Local VAD / ASR / Event Detection
       ↓
Structured State Delta
       ↓
Jev-like Decision Model
       ├── Silent
       ├── Defer
       ├── Minimal Cue
       └── Escalate to Pi
                    ↓
              Reasoning LLM
                    ↓
             Guidance Candidate
                    ↓
           Intervention Controller
```

其中普通程序可以直接决定的事情，无需调用模型。

例如：

- 剩余演讲时间的计算；
- 幻灯片切换事件；
- 提示冷却时间；
- 已过期的建议；
- 用户是否关闭实时指导。

只有存在真正语义判断需求的事件，才需要进入模型路径。

隐私架构

用户应能清楚看到哪些数据源正在被采集。屏幕和麦克风分别授权；支持快捷暂停、关闭记录、删除会话；不默认保存完整音视频。涉及第三方的真实社交对话，还要满足相应的知情同意要求。

同时，给 Pi 的上下文应主要是经过筛选的任务事件，而不是未经处理的全部个人屏幕历史。

## 八、创新性判断：哪些部分已经有人做过？

有一个直接相关的先例值得特别注意。

TypeSafe 官方已经提供一个名为 **[Intelliprompter](https://docs.typesafe.ai/cookbooks/intelliprompter?utm_source=chatgpt.com)** 的示例：通过语音转写，实时检查演讲者是否覆盖预定的内容要点，并用 Jev Score 更新完成状态。\[[Intelliprompter](https://docs.typesafe.ai/cookbooks/intelliprompter?utm_source=chatgpt.com)\]

这意味着：

**“实时监听演讲并检查内容覆盖”已经不是一个足够新颖的核心创新。**

我们需要把差异化放在更高一层。

| 普通实时 AI 提示 | RealtimeGuide 的目标 |
|--------|--------|
| 判断有没有发生错误 | 判断错误是否值得现在干预 |
| 检测到事件就提醒 | 允许沉默、延迟和事后指导 |
| 以生成建议为中心 | 以干预决策为中心 |
| 关注当前表现 | 区分当前表现和长期学习 |
| 只展示反馈内容 | 展示可验证的干预决策与效果 |
| 依赖单一场景逻辑 | 通过 GuidePack 复用核心机制 |

我认为这才是产品的差异化，也是值得拿去做技术答辩的部分。

## 九、针对苏客松的 MVP 取舍

目前赛制下，我会优先做一个完整的演讲场景，而不是三个半成品。

P0

**必须完成：演讲闭环**

用户上传 PPT 或输入演讲提纲，启动语音监听，系统追踪时间和内容覆盖，决定是否给予短提示，结束后生成可定位到时间点的复盘。

P1

**值得完成：干预策略对照**

同一段预录演讲事件流，分别由固定提示策略与 Jev-like 自适应策略处理，展示两个系统不同的决策及其理由。

P2

**有余力再做：数学 GuidePack**

加入一个结构化解题工作区，验证相同的事件-决策-指导-复盘机制能够迁移到另一个任务领域。

黑客松现场最好能提供两种 Demo：一种是评委亲自说话、实时触发；另一种是确定性的预录事件回放。后一种不是为了伪装实时能力，而是为了稳定展示干预策略的差异，避免现场网络和语音识别波动影响评审。

而且我建议将实验指标定得非常具体：

- **False Intervention Rate**：每十分钟不必要的打断次数。
- **Missed Opportunity Rate**：已经明确标注、但被系统漏掉的合理干预机会比例。
- **Decision Latency**：事件被识别后到策略决策完成的延迟。
- **Intervention Acceptance**：用户是否觉得提示时机和形式合适。
- **Independent Performance**：撤除 AI 后，用户独立完成任务的表现。

前四个比较适合黑客松 MVP。最后一个需要后续更严谨的实验，不应直接宣称已经验证。

## 十、最终产品定位

我认为 RealtimeGuide 可以形成一个比较清晰的产品层次：

## RealtimeGuide

An Agent-Native Cognitive Companion

---

面向用户

一个理解你正在做什么、知道什么时候应该帮助你，也知道什么时候应该保持沉默的 AI。

---

面向开发者

一个可以使用 GuidePack 扩展的实时任务观察与智能干预平台。

---

面向研究

一个能够记录、评估和优化人机干预策略的实验系统。

长期来看，它可以超越教育，扩展到软件操作指导、工作流辅助、专业技能训练和无障碍交互。

但我建议首个产品仍然以 **AI Education / Skill Training** 为核心定位，因为这使“为什么不能始终给出答案”成为一个自然的产品问题，而不是人为添加的限制。

### 我认为需要坚持的三个架构决策

**第一，Jev-like System 1 负责决策信号，而不是直接控制用户行为。** 这能控制模型不确定性带来的风险。

**第二，Pi Agent 负责复杂认知工作，不进入必须严格低延迟的热路径。** 这能够避免工具调用和生成式推理拖慢用户的实时体验。

**第三，Reflection 不是附属功能，而是与 Live Companion 同等重要的产品核心。** 因为有些任务中，最好的实时干预恰恰是沉默。

最终，我觉得 RealtimeGuide 真正值得构建的，不是一个“无时无刻不在提醒你的 AI”。

而是一个 **Cognitive Intervention Operating Layer（认知干预操作层）**：

它能够持续理解用户正在进行的任务，将外部 AI 的认知能力转化为适时、适量、可控的帮助，同时尽可能保留用户自己的注意力、决策权和学习机会。

这套架构既能支撑此次黑客松的可运行 Demo，也为之后针对干预策略、反馈时机和人机认知协作的研究留下空间。

### 我建议的完整路演文案

**document: **

# RealtimeGuide · 三分钟产品路演

大家有没有经历过这样的时刻？

你准备好了一场演讲，甚至在脑海里已经演练过很多遍。但真正站在台上时，你突然发现，时间快不够了，重要的内容却还没有讲到。

或者，你在做一道数学题。你实际上知道正确的方法，但在某一步不小心犯了错误，之后的推导全部偏离了方向。

我们已经拥有非常强大的 AI。它们可以解释知识、分析问题，甚至替我们完成复杂任务。

**但是，有一个问题始终存在：当你正在执行任务时，你真的有机会停下来向 AI 提问吗？**

而如果 AI 不断主动给你提示，又会产生一个新的问题：它正在占用你原本就有限的注意力。

我们认为，下一代 AI 助手，不应该只是能够回答问题。

**它应该理解你正在做什么，并知道什么时候应该帮助你，什么时候应该保持沉默。**

这就是 RealtimeGuide。

RealtimeGuide 是一个 Agent Native 的实时认知辅助系统。

它持续观察用户授权的任务环境，理解任务进度，识别潜在问题，并自主决定是否、何时以及如何介入。

例如，在一次演讲中，系统发现用户剩余时间不足，但不会立刻弹出一大段建议。

它可以等待用户完成当前表达，在切换幻灯片时，给出一句简短的时间提醒。

而当任务结束后，RealtimeGuide 会把过程中的关键事件重新呈现出来，帮助用户理解自己哪里可以做得更好，并针对具体场景重新练习。

**我们的重点不是让 AI 说得更多，而是让每一次干预都有价值。**

技术上，我们采用快速决策模型与 Pi Agent Harness 协同的架构：快速路径负责状态判断和干预选择，复杂 Agent 负责深度推理、工具调用和复盘。最终通过独立的干预控制层，确保系统行为可控。

今天我们从演讲场景开始，但这套机制可以扩展到解题、社交训练和其他需要实时认知支持的任务。

我们希望探索的是一种新的 AI 交互方式：

**从你主动寻找 AI 的答案，变成 AI 在你真正需要的时候，提供恰到好处的帮助。**

这就是 RealtimeGuide。

这份稿子可以作为基础，但现场应该用实际 Demo 代替其中部分口述。尤其不要花大量时间解释 Pi Agent 的内部实现，把时间留给评委看见产品行为。

## 四、我认为有三个必须突出的故事细节

### 1\. 不只是“AI 发现了错误”，而是“AI 面临了一个选择”

如果故事是：

用户犯错 → AI 发现 → AI 提醒。

那它与传统 AI 实时辅导没有本质差异。

应该改成：

用户犯错 → AI 发现 → AI 判断用户是否能够自主纠正、当前能否接受反馈 → AI 决定如何行动。

在这个版本里，Agent 的决策才是真正的主角。

### 2\. 故事中必须出现一次沉默

最好把沉默作为有意设计的展示环节。

例如：

“现在 RealtimeGuide 已经发现了一个问题。但大家注意，它并没有弹出提示。因为用户正在讲话，这时候打断可能比问题本身造成更大的影响。”

这段解说能够让评委直接理解 Intervention Policy，而不必先知道 POMDP、System 1 或 Jev 是什么。

### 3\. 结尾应该回到人，而不是回到 AI

如果故事停在“我们使用先进的双速 Agent 架构”，会比较可惜。

应该把结尾落到长期价值：

**今天，RealtimeGuide 帮你完成一场更好的演讲。明天，我们希望它能帮助你成为一个即使没有 RealtimeGuide，也能独立完成更好演讲的人。**

这两者必须区分：前者是当前辅助目标，后者是尚需验证的教育愿景。

它自然承接了此前 Performance Mode 与 Learning Mode 的设计。

## 一、首先必须区分：Performance ≠ Learning

这不是我们自己提出的概念，而是学习科学中一个非常重要的区分。

2015 年，Soderstrom 与 Bjork 在《Perspectives on Psychological Science》发表的综述 *Learning Versus Performance* 指出：

- **Performance（表现）**：学习或训练过程中能够直接观察到的行为与成绩。
- **Learning（学习）**：支持知识与技能长期保持、在其他情境中灵活运用的相对持久变化。

研究表明，训练期间表现的改善有时并不能转化为持久学习；反过来，某些有利于长期学习的训练方式，甚至可能暂时降低练习时的表现。\[[Learning Versus Performance - Nicholas C. Soderstrom, Robert A. Bjork, 2015](https://journals.sagepub.com/doi/pdf/10.1177/1745691615569000?utm_source=chatgpt.com)\]

这意味着，我们需要严格区分三个层次。

LEVEL 1 · ASSISTED PERFORMANCE

**用户在 AI 帮助下完成了一次社交任务。**

证明的是用户在辅助条件下能够完成任务，而不是掌握了能力。

LEVEL 2 · INDEPENDENT PERFORMANCE

**撤除 AI 后，用户能独立处理一个新情境。**

提供了初步学习或近迁移的证据，但仍无法确定能力是否持久。

LEVEL 3 · RETENTION &amp; TRANSFER

**经过一段时间，用户仍然能够在不同的真实情境中自主运用能力。**

这是更有说服力的学习效果证据，需要延迟测试和情境迁移测试。

你现在反对的，是我们在路演中从 Level 1 直接跳到 Level 3。

**这个反对完全成立。**

而且针对 RealtimeGuide，这个问题可能比传统 AI Tutor 更严重。

因为我们设计的是一个持续感知、主动提示的 Agent。它有可能将用户的即时任务表现改善得非常明显，却让用户更加依赖外部提示。

2025 年发表于《PNAS》的一项近千名高中数学学生参与的现场实验就发现：常规 GPT 辅助提高了学生练习时的成绩，但在随后撤除 AI 的考试中，相关学生的平均表现反而低于未使用 AI 的对照组。经过教学约束的 GPT Tutor 缓解了这一问题，但并未显示出明确的独立考试成绩优势。\[[Generative AI without guardrails can harm learning: Evidence from high school mathematics](https://pubmed.ncbi.nlm.nih.gov/40560616/?utm_source=chatgpt.com)\]

所以我们必须承认：

**实时指导的成功，不仅不等于教育的成功，甚至在某些条件下可能与教育目标发生冲突。**

## 二、但我想反驳：“教育是长期目标”不意味着“短时间内没有教育”

假设一个学生原本不知道如何解一类方程。

老师用了五分钟解释。

学生随后能够独立解出一道结构相似但数字不同的题。

我们能不能说这五分钟发生了学习？

**可以认为我们获得了初步学习证据。**

但如果学生第二天完全忘记了，或者只会模仿原题，那么这次教学的长期效果就很有限。

所以这里最重要的区分是：

**学习发生所需的时间，与证明学习效果具有持久性所需的时间，不是同一个量。**

一个新的理解可能在几秒内形成，但其稳定性和可迁移性需要后续观察。

2006 年 Roediger 与 Karpicke 关于提取练习的实验很能说明问题：在五分钟后的测试中，重复学习可能表现更好；但在两天或一周后的测试中，之前接受提取练习的组表现更好。也就是说，立即测得的优势不一定能预测后来的学习保持。\[[Test-enhanced learning: taking memory tests improves long-term retention](https://pubmed.ncbi.nlm.nih.gov/16507066/?utm_source=chatgpt.com)\]

因此，我不赞同把教育定义为“必须经过很长时间才能发生的活动”。

更合理的定义是：

> **教育是有目的地组织学习经验，以促进学习者知识、技能、判断与自主能力发展的过程。它可以在短时间内发生，但其长期成效需要相应的证据验证。**

这里还要区分“教育活动”与“教育有效性已得到验证”。

老师上了一堂课，这是教育活动，不需要首先完成随机对照试验才能称为教育。

但如果老师宣称“我的教学方法显著优于其他方法”，那就需要充分的比较证据。

同样，RealtimeGuide 完全可以定位为教育产品，但不能因为展示了一次成功指导，就宣称已经证明了教育效果。

## 三、重新理解教育：它不是把一次任务做对

我想进一步挑战我们过去的产品思路。

我们一直把问题描述成：

“用户已经知道如何做，但无法在真实环境中及时执行。”

这个描述并没有错，但它隐含了一个问题：

**我们是不是把教育理解成了某种正确行为的训练？**

尤其在社交场景中，这个假设值得警惕。

例如，一个人在小组讨论中没有积极发言。我们能否认为他社交能力不足？

不能。

他可能是没有理解讨论内容，也可能选择倾听，或者不认同讨论目标。

因此，教育不能简单等同于提高某类行为的发生频率。

至少对于社交教育，我们应该区分：

- **知识**：是否理解不同沟通策略及其适用条件。
- **技能**：是否能够在具体情境中组织表达、倾听、提问或处理分歧。
- **判断**：是否知道何时适合采取哪种行动。
- **自主性**：是否能根据自己的目标和价值，而不是机械执行系统建议。

其中，自主性十分重要。

如果 AI 训练一个人，使他在任何对话中都习惯性地迎合对方，这个人可能在某些算法评分里表现更好，但我们很难说这就是好的教育。

所以我认为 RealtimeGuide 的教育目标不应该是：

“让用户表现得更符合 AI 认为正确的社交规范。”

而应该是：

**让用户在理解自身目标和情境的基础上，获得更多自主选择与有效行动的能力。**

这也重新解释了 System 1 的地位。

我们不是为了把用户训练成一个自动执行固定反应的系统。

我们希望的是：熟悉的技能可以被高效调用，而面对复杂、不确定或不适合立即反应的情境时，用户仍然能够主动判断和调整。

## 四、如果坚持教育定位，产品必须具有真实的教学机制

这是我认为应当对当前 RealtimeGuide 进行的最重要修改。

此前的主要流程是：

观察  推理  指导  复盘

这可以构成一个优秀的实时辅助产品。

但它**本身并不足以构成一个完整的教育机制**。

因为其中缺少一个关键环节：学习者在接受帮助之后，能否在没有帮助的情况下重新执行？

我建议将产品的核心闭环改成：

**1\. Baseline · 独立前测**

先观察学习者在没有 AI 帮助时，面对具体任务的真实表现。

**2\. Guided Practice · 情境化训练**

持续观察任务，根据学习者表现决定何时提供提示、何时允许自主尝试。

**3\. Reflection · 证据驱动的复盘**

通过具体事件帮助学习者理解为什么一种行为有效、在什么条件下可能无效。

**4\. Independent Retry · 撤除帮助后的新情境练习**

用户在变化过的情境中自主运用刚才的知识和技能。

**5\. Retention &amp; Transfer · 延迟保持与迁移**

在之后的独立测试中评估技能是否保持，以及能否在其他情境中应用。

这个设计对应教学研究中的 *Scaffolding*（支架式教学），特别是三个重要机制：根据学习者状态调整帮助、逐步撤除帮助、把任务责任移交给学习者。\[[Scaffolding in Teacher–Student Interaction: A Decade of Research \| Educational Psychology Review](https://link.springer.com/article/10.1007/s10648-010-9127-6?utm_source=chatgpt.com)\]

现在 RealtimeGuide 的意义发生了变化：

实时监测与实时推理，不只是为了在用户出错时给出建议。

它们还用于判断学习者目前处于什么能力水平、是否需要支持，以及何时可以把控制权交还给学习者。

这时 Jev-like System 1 和 Pi Agent Harness 才真正成为教学机制的组成部分，而不只是辅助工具的技术堆栈。

## 五、特别针对社交：我们真正需要证明的是迁移

假设用户正在学习如何应对小组讨论中的突发质疑。

我们可以把一个很大的目标：

“提高社交能力”

收缩为一个可以观察的微技能：

“当别人质疑自己的观点时，能够识别质疑的具体内容，并在需要时先澄清问题，再组织回应。”

这当然不是完整社交能力，只是一个便于训练和评估的具体目标。

然后设计三种情境：

情境 A

前测

队友对方案的成本提出质疑。

无 AI 指导，观察回应。

情境 B

训练

队友对方案的技术可行性提出质疑。

允许提示与事后复盘。

情境 C

迁移测试

另一位队友对时间安排提出质疑。

撤除帮助，再次观察。

如果用户在情境 C 中，能够独立识别问题并作出更合适的回应，我们获得了什么？

**我们获得了初步的近迁移证据。**

但我们依然不能声称：

“用户现在已经具备了真实社交能力。”

因为他可能只是刚刚记住了某种回应方式，也可能仅仅适应了 AI 模拟环境，甚至可能只是在第二次测试中更熟悉评估规则。

实际社交涉及不同的人、关系、利益、情绪和文化背景。模拟场景中的进步未必自动迁移到这些复杂环境。

相关研究也印证了这个难点。例如 2025 年的一项沉浸式 VR 社交沟通训练系统综述认为，已有研究显示出积极潜力，但真实情境迁移和长期效果的评估依然不足。\[[Applications of Virtual Reality to Support Social Communication in Individuals with Autism: A Systematic Review of Immersive Interventions](https://www.mdpi.com/2078-2489/16/11/941?utm_source=chatgpt.com)\]

因此，如果我们要做一个真正严谨的社交教育 Agent，必须把以下三个问题长期保留下来：

**练习中是否做得更好？撤除帮助后是否仍然会做？离开我们的模拟环境以后是否还会用？**

这三个问题不可以用同一份 Demo 数据回答。

## 六、那么，三分钟路演到底能够证明什么？

我认为应该建立一个明确的**证据等级**，而不是试图用三分钟证明整个教育命题。

| 证据等级 | 我们可以展示什么 | 可以作出的声明 |
|--------|--------|--------|
| 1\. 技术可行性 | 系统持续识别任务事件，并选择是否干预 | 我们实现了一个可运行的实时干预系统 |
| 2\. 交互可用性 | 用户能够接收并理解提示，系统支持复盘 | 我们实现了完整的辅助与训练交互 |
| 3\. 初步学习迹象 | 用户在撤除 AI 后完成新的模拟任务 | 观察到了值得进一步验证的独立表现变化 |
| 4\. 教育效果 | 多人对照实验、延迟保持与迁移测试 | 在指定人群和任务中发现了学习收益 |
| 5\. 真实世界有效性 | 多环境、较长时间的实际行为验证 | 具备更强证据支持的真实应用效果 |

以目前的黑客松阶段，我认为**应该保证第 1、2 级，尝试第 3 级，不声称完成第 4、5 级**。

而且必须明确：哪怕一个用户在前测后测中进步了，也不能确定这种进步是 RealtimeGuide 导致的。测试熟悉度、练习本身、任务难度等都可能影响结果。

要证明因果效果，还需要合理的对照条件和足够的样本。

这不是对项目的削弱，而是让我们真正知道自己完成了什么。

## 七、我建议重写产品路演的核心论证

之前我们倾向于讲：

> 我们利用 AI 实时指导用户，通过不断纠错，让他们真正学会社交。

这个说法存在两个问题。

首先，即时纠错不一定促进长期学习。

其次，社交能力的形成不能通过一次短暂演示得到验证。

我建议改成下面这个版本：

**standard: **

我们发现，当前的 AI 已经非常擅长告诉人们应该如何完成一项任务。

但知道如何做，与真正能够独立做到，并不是一回事。

尤其是在社交、演讲、即时表达这些场景中，学习者可能理解了所有理论，却无法在真实情境中及时运用。

我们希望探索一种新的 AI 教育方式。

**不是让 AI 替用户完成任务，而是让 AI 在用户实际练习的过程中，提供恰当的支持，并逐步撤除支持。**

这就是 RealtimeGuide。

它通过持续观察任务、实时推理和智能干预，在练习中帮助用户发现问题。它也能够主动保持沉默，让用户独立思考，并在任务结束后进行有针对性的复盘。

更重要的是，我们不仅关注用户在 AI 帮助下表现得怎么样，也关注他们在没有 AI 的情况下，能否独立完成新的任务。

今天，我们展示的是一套能够运行的实时感知、自适应指导、复盘和独立练习系统。

**我们还不能宣称它已经证明了长期教育效果。**

但我们希望提供一种可验证的教育技术路径：让 AI 的价值不只体现在它给出的答案上，也体现在学习者逐渐获得的自主能力上。

我们的最终目标，是让用户在使用 RealtimeGuide 之后，能够越来越少地依赖 RealtimeGuide。

我认为这种叙事比“我们创造了一种能够提高社交能力的 AI”更加可信，也更加具有研究价值。

它主动承认了尚未解决的问题，同时明确指出了现在已经能够展示的贡献。

## 八、一个更深刻的反驳：教育甚至未必需要以长期行为改变作为唯一价值

还有一个哲学层面的疑问。

假设 RealtimeGuide 帮助一个从来不敢在小组讨论中表达意见的人，第一次成功说出了自己的观点。

但第二天，这个人面对类似场景仍然紧张，仍然没有办法独立表达。

那么昨天的经历毫无教育价值吗？

我认为不能如此判断。

因为这次经历可能已经改变了他对自身能力的认识，提供了新的经验，或者促使他产生继续练习的意愿。

当然，这些都需要观察，不能自行假设它们已经发生。

我们可以进一步把教育价值区分为：

**能力发展（Capability Development）**：用户是否真正获得可保持、可迁移的能力。

**主体性发展（Agency Development）**：用户是否获得更多理解、选择、尝试与自主行动的可能性。

二者相关，但不完全相同。

教育不只是提高某个指标，更不应该只是让用户成为符合 AI 预设行为标准的人。

对于社交这样的领域，我尤其认为主体性非常重要。

用户应该有能力选择是否表达、如何表达、何时拒绝，而不是学习一种单一的“正确社交反应”。

这也意味着，RealtimeGuide 不应该把目标设定为消除一切停顿、沉默和表达犹豫。

这些行为有时完全合理。

# 第一部分：继续推导产品叙事

## 2\. 为什么传统学习方式没有充分解决这个问题？

先看目前人们通常如何学习一项技能。

## 传统技能学习路径

**Learn**

学习理论与知识

**Practice**

在相对可控的环境中练习

**Evaluate**

通过结果评价学习表现

**Apply**

尝试应用于真实环境

这是一个概括性的学习流程，并非所有教育体系都采用相同顺序。

问题在于，练习环境与真实环境之间可能存在很大差异。

例如：

- 练习社交时，对手是一个愿意配合你的 AI；真实社交中，对方有自己的目标。
- 练习演讲时，你可以反复暂停；正式演讲中，时间持续流逝。
- 练习解题时，你知道正在练习哪种题型；真实考试中，你需要先判断应该使用什么方法。

这意味着，学习者面对的并不只是知识难度，而是环境复杂性、信息不确定性和行为时限。

我认为这里有一个重要的产品机会：

**把 AI 从知识传授者，变成学习者真实任务与练习过程中的持续参与者。**

传统 AI Tutor 主要解决：

> What should I know?

RealtimeGuide 希望进一步解决：

> How can I actually do it, when it matters?

## 3\. 为什么是现在？

过去，建立这种产品存在几个技术障碍：

1. AI 对连续语音、视觉和屏幕信息的理解能力有限。
2. 实时推理成本高，难以持续运行。
3. Agent 缺少可靠的状态管理和长期上下文。
4. AI 提示难以根据任务状态动态调整。
5. 不同技能需要不同的专业工具和评价体系。

现在，多模态模型、低延迟语音交互、结构化决策模型以及 Agent Harness 的发展，让我们可以开始尝试构建这种系统。

这里真正发生的变化不是 AI 突然学会了教育。

而是：

**AI 开始有机会持续参与一个任务，而不再只是等待用户提出一个问题。**

这就是 Agent Native 在产品层面的意义。

## 4\. RealtimeGuide 究竟要提供什么？

我们可以把产品重新描述成三个层次。

**Experience the situation**

让用户进入真实或高度仿真的任务情境，而不是只在聊天框中讨论如何完成任务。

---

**Understand and guide**

AI 持续理解任务状态，根据情况选择指导、提示、调整练习，或者保持沉默。

---

**Reflect and grow**

把一次次具体经历连接起来，让用户理解自己的行为、形成新的策略，并继续挑战。

注意，这里不是简单的“AI 监控人类”。

用户始终是任务的主体。Agent 的角色是提供支持，而不是接管用户的判断和行为。

## 5\. 我们真正想改变的是什么？

我认为产品愿景应该再往前一步。

传统教育产品通常把知识、课程、题目作为组织中心。

而 RealtimeGuide 可以尝试把**人的能力发展**作为组织中心。

例如，一个用户的目标不是完成十节沟通课程，而是：

- 能够清晰表达自己的观点；
- 能够处理不同意见；
- 能够在陌生环境中组织表达；
- 能够识别什么时候需要倾听，什么时候需要回应；
- 能够自主判断自己的行为是否符合目标。

课程、模拟、AI 指导、真实任务、复盘，都成为服务于这些目标的工具。

这使 RealtimeGuide 不只是一个 AI 教师，而更像一个长期陪伴用户进行技能发展的个人 Agent。

我建议将这个愿景表述为：

> **An AI companion that helps people turn knowledge into capability through real-world practice, adaptive guidance, and continuous reflection.**

一个通过真实任务练习、自适应指导和持续复盘，帮助人们将知识转化为能力的 AI 伴随系统。

## 10\. 一个非常重要的市场发现：企业培训可能比个人教育更容易成为早期市场

这里我想提出一个可能与你最初设想不同的判断。

RealtimeGuide 的长期愿景可以是面向所有人的个人能力发展 Agent，但**第一个商业化市场未必应该是 C 端学生。**

我们来看两个市场。

**B2C · 个人能力发展** (长期愿景)

用户：大学生、求职者、职场新人、希望改善沟通能力的人。

用户需求：

- 希望提高表达和沟通能力。
- 希望更好地应对陌生情境。
- 希望得到个性化、持续的指导。
- 不想购买昂贵的私人教练服务。

**商业挑战：** 用户付费意愿、长期留存、真实能力提升难以量化，以及个人数据隐私。

**B2B · 企业技能培训** (值得优先验证)

客户：企业 L&amp;D、销售培训、人力资源、客服团队、培训机构。

用户需求：

- 大量员工需要重复练习相似技能。
- 人类教练难以持续观察每个人。
- 培训结果需要量化。
- 希望降低培训成本和新人上岗时间。

**商业优势：** 预算归属相对明确，企业有现成培训流程，技能标准和评估指标相对容易定义。

这并不是说 B2B 一定更好，而是现有市场已经提供了较强的商业验证。

例如：

- Yoodli 提供企业按席位收费、团队分析、定制训练和 LMS 集成。\[[Pricing &amp; Plans](https://example.yoodli.ai/pricing?utm_source=chatgpt.com)\]

我建议：

- 长期愿景：个人能力发展 Agent。

## 11\. 市场空白究竟在哪里？

调研之后，我认为需要修正之前一个过于乐观的判断：

不能说 Yoodli、Second Nature 等产品没有长期学习规划、个性化指导或持续评估。

事实上，它们已经在做这些事情。

Yoodli 现在甚至具有 Coach、Measure、Roleplays 等相互配合的产品模块，能够在练习过程中组织后续训练，并跟踪团队能力变化。\[[Yoodli \| AI Roleplays for Sales Training, Onboarding and L&amp;D](https://yoodli.ai/?utm_source=chatgpt.com); [Pricing &amp; Plans](https://example.yoodli.ai/pricing?utm_source=chatgpt.com)\]

Second Nature 也已经把课程、情境模拟、个性化反馈和进度分析整合起来。\[[AI Sales Role Play Platform for Enterprise](https://secondnature.ai/product/?utm_source=chatgpt.com)\]

因此，RealtimeGuide 的竞争优势不能简单建立在：

- 我们有长期记忆；
- 我们能生成模拟场景；
- 我们能给出个性化反馈；
- 我们能分析用户表现。

这些都已经是市场上逐渐成熟的能力。

我认为还有三个值得探索的方向。

(机会 A)

**从训练场景走向真实任务伴随**

现有产品通常围绕可控的训练会话或特定会议场景组织体验。

RealtimeGuide 希望进一步研究：能否在用户授权的真实任务中持续理解情境，将真实经历和训练过程连接起来。

这不是说竞品完全没有实时能力，而是尝试把真实任务与技能发展建立更统一的关系。

(机会 B)

**干预策略本身成为产品核心**

大部分产品强调分析、评分和生成建议。

RealtimeGuide 希望将「是否应该干预、什么时候干预、采用什么强度」作为独立的决策问题。

这可能是 Jev-like System 1 最值得发挥的地方。

(机会 C)

**跨场景的能力发展底座**

今天用户练习演讲，明天练习面试，后天参加团队讨论。

不同任务可以拥有独立的 GuidePack，但共享用户目标、历史经验和能力发展上下文。

我们希望最终构建的不是三个独立 AI 工具，而是一个能够适应不同技能领域的个人 Agent。

这里需要把“机会”与“已验证的市场空白”区分开。目前它们是值得验证的产品假设，不能宣称竞争者都没有这些能力。

## 12\. 我们还应该关注哪些趋势？

我认为有三个趋势对 RealtimeGuide 特别重要。

**趋势一：AI 从内容生成走向技能训练。**

2025 年的两项研究给出了不同但互补的信号：

- Harvard 团队在《Scientific Reports》发表的随机对照实验发现，设计良好的 AI Tutor 可以在大学物理教学中取得优于传统主动学习课堂的学习结果。\[[AI tutoring outperforms in-class active learning: an RCT introducing a novel research-based design in an authentic educational setting](https://doi.org/10.1038/s41598-025-97652-6?utm_source=chatgpt.com)\]
- PNAS 的高中数学现场实验则表明，不加教学约束的 AI 辅助可能损害撤除 AI 后的独立表现。\[[Generative AI without guardrails can harm learning: Evidence from high school mathematics](https://pmc.ncbi.nlm.nih.gov/articles/PMC12232635?utm_source=chatgpt.com)\]

两项研究并不矛盾。它们共同说明：**AI 对学习的价值取决于具体的教学设计，而不是模型本身有多强。**

**趋势二：企业开始关注训练效果，而不仅是训练完成率。**

Second Nature 和 Yoodli 都在强化团队表现分析、能力评估和进度跟踪。\[[AI Sales Role Play Platform for Enterprise](https://secondnature.ai/product/?utm_source=chatgpt.com); [Pricing &amp; Plans](https://example.yoodli.ai/pricing?utm_source=chatgpt.com)\]

这意味着未来竞争不只是“谁的 AI 角色扮演更逼真”，还包括谁能够更好地证明培训是否产生了有意义的变化。

**趋势三：实时辅助和事后训练正在融合。**

Poised 的产品方向就同时包括会议实时反馈、Speaker Notes 和事后改进建议。它也恰好说明实时伴随并不是 RealtimeGuide 独有的想法。需要说明的是，Poised 官网确实显示其服务已于 2026 年 10 月 8 日停止，这里不能将它当作仍在正常运营的竞争者。\[[Poised: AI-Powered Communication Coach](https://poised.com/?utm_source=chatgpt.com)\]

此外，Orai 2026 年的竞品分析也将实时会议反馈、AI 角色扮演、事后反馈和持续练习视为不同的产品工作流。该文章由 Orai 自己发布，属于厂商视角，不能当作独立市场研究。\[[6 Best AI Speech Coach Apps in 2026](https://orai.com/blog/best-ai-speech-coach-apps/?utm_source=chatgpt.com)\]

## 16\. 最后一个重要问题：市场规模与商业模式

目前我们已经找到相邻产品、价格和企业客户，但还没有足够可靠的数据给 RealtimeGuide 直接估算一个精确 TAM。

| 维度 | B2C 个人用户 | B2B 企业客户 |
|--------|--------|--------|
| 核心价值 | 个人成长与能力提升 | 员工技能与业务表现 |
| 收费方式 | 订阅制 | 按席位、使用量或项目收费 |
| 主要成本 | 推理、语音、存储 | 部署、集成、安全、推理 |
| 留存驱动 | 能力成长、日常使用 | 培训效果、组织流程嵌入 |
| 核心风险 | 用户流失、付费意愿 | 销售周期、采购和隐私审查 |

我建议黑客松阶段先不做价格承诺，而是通过 Demo 观察用户究竟愿意为什么付出成本：

- 他们愿意为实时辅助付费吗？
- 他们愿意为持续的技能训练付费吗？
- 他们更在乎某一次任务的表现，还是长期能力发展？
- 企业是否愿意把它嵌入现有培训流程？

这几个问题比一个未经验证的 TAM 数字更有价值。

# 一、整体产品形态：不是仪表盘，而是练习空间

首页不应该是空白聊天框，也不应该堆满指标。它首先邀请用户完成一项具体任务：

### 演讲练习
**“把下一次，讲得更好。”**

输入主题、听众、时长和三个关键点，开始一场演讲。

### 算法练习
**“把思路，变成自己的能力。”**

打开一道题，独立思考、编写代码、运行测试。

两个入口都进入相同的三个阶段：

**设定目标 → 实时练习 → 复盘与重练**

这让评委理解：我们不是同时做一个演讲软件和一个刷题网站，而是在展示一种能够适配不同任务的陪练方式。

## 两种视图必须分开

这里需要解决一个明显矛盾：**你希望展示丰富参数，但正在演讲的人不应该盯着这些参数。**

因此我设计了两个视图：

| 视图 | 主要使用者 | 显示内容 |
|---|---|---|
| **专注视图** | 正在练习的用户 | 任务画面、时间、简洁进度、必要时出现的一条提示 |
| **演示视图** | 评委、开发者、体验观察者 | 在专注视图旁增加事件、判断依据、策略参数和系统状态 |

MVP 用一个开关切换即可。以后可以让用户看主屏，评委在另一块屏幕上看观察窗。

**“系统正在思考什么”可以被展示，但不应该成为用户完成任务时的额外负担。**

# 二、主场景：摄像头前的一次演讲

## 1. 开始前：设定一份最小任务契约

第一版不必把上传 PPT、自动解析和生成讲稿全部做进去。直接让用户提供：

| 项目 | 示例 |
|---|---|
| 演讲题目 | RealtimeGuide：从知道，到做到 |
| 听众 | 黑客松评委与开发者 |
| 时长 | 3 分钟 |
| 关键点一 | 用户知道怎么做，却无法在现场做到 |
| 关键点二 | 持续观察、选择性提示、事后复盘 |
| 关键点三 | 帮助用户获得独立完成任务的能力 |
| 辅助方式 | 自适应陪练／仅事后复盘 |

这里有一个产品细节：**提纲是系统理解目标的参照，不是要求用户照着念的台词。**

随后分别开启摄像头和语音转写。摄像头权限需要用户授权，并在安全上下文中使用；本地开发可以通过 `localhost` 提供页面。([MDN Web Docs](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia))

### 摄像头在第一版里负责什么？

我建议它先承担**现场演练的画面载体**，而不是承担所有智能判断。

演讲内容主要由语音转写和提纲判断。摄像头让用户进入演练状态，也支持隐藏自身画面，避免用户一直观察自己的表情。

**不必为了“多模态”而加上未经支撑的紧张度、专注度、社交能力识别。** 后续确实需要姿态或演示动作反馈时，再单独扩展。

## 2. 演讲中：主画面与 HUD

这是已经做出的演讲界面：

![RealtimeGuide 演讲原型](sandbox:/mnt/data/realtimeguide-live.png)

主区域是摄像头画面，未开启时显示练习占位画面。上方放计时，下方放三个内容要点；真正需要帮助时，只出现一张短提示卡片。

例如：

> **回到核心：AI 何时该介入？**

或者：

> **还剩 29 秒，请收束到愿景。**

不出现整段建议，不自动朗读，不持续刷屏。

右侧演示面板则可以显示：

> 当前发现了一个偏题候选，但用户仍在连续表达，因此等待。

这句话**只给观察者看，不弹到演讲者眼前**。

# 三、演讲 Demo 的核心：必须让“不提醒”有故事

我建议不要只演示“我故意偏题，AI 马上弹窗”。那样更像一个检测器。

完整 Demo 应当有两次偏题，并给出不同处理。

| 时刻 | 用户行为 | 系统处理 | 用户 HUD |
|---|---|---|---|
| 开始 | 正常介绍问题 | 追踪提纲，继续观察 | 无提示 |
| 第一次偏题 | 短暂谈到黑客松现场的其他事情 | 产生候选，暂缓提醒 | 无提示 |
| 自行回归 | “回到我们的产品……” | 取消刚才的候选 | 仍然无提示 |
| 第二次偏题 | 持续展开无关内容 | 等待发言边界，保留候选 | 暂不提示 |
| 出现停顿 | 当前句子结束，候选仍有效 | 发出一句轻提示 | 提醒回到核心 |
| 接近结束 | 时间不足，愿景尚未表达 | 在过渡位置给出时间提醒 | 提醒收束 |
| 演讲结束 | 用户完成任务 | 进入事件复盘 | 不再补发旧提示 |

**第一个记忆点：系统已经发现问题，却没有打断。**

**第二个记忆点：用户自己解决了问题，系统把准备好的提示取消了。**

**第三个记忆点：真正需要帮助时，系统才出现。**

这三个时刻连起来，才能体现 RealtimeGuide，而不仅是实时语音分析。

## 偏题判断需要有上下文

正式模型版不能只问：

> “这一句话与演讲题目相似吗？”

更合适的是：

> “结合当前论点和最近几段发言，这段内容是在解释、举例、过渡，还是持续离开任务目标？”

合理的例子可能暂时没有出现主题关键词，因此需要允许短暂偏离，并允许后续回归取消提醒。

当前原型使用关键词基线；预置演示中的相关度明确标为脚本。之后换成 Jev-like 判断层时，界面和干预流程不需要重做。

TypeSafe 官方已有根据演讲转写追踪提纲覆盖的 Intelliprompter 示例，可以作为内容追踪的实现参考；我们的展示重点应进一步放在**覆盖结果如何影响等待、取消、提示和复盘**。([TypeSafe](https://docs.typesafe.ai/cookbooks/intelliprompter))

# 四、参数应该展示，但要展示“真正有用的参数”

我建议观察窗包含三类信息，而不是一排看起来很科学的百分比。

| 类型 | 推荐显示 | 作用 |
|---|---|---|
| **任务事实** | 经过时间、剩余时间、内容要点、实际测试结果 | 说明发生了什么 |
| **判断信号** | 内容相关性、要点覆盖、候选问题、可见任务边界 | 说明系统如何理解当前状态 |
| **干预配置** | 冷却时间、提醒预算、连续偏离窗口、过程提醒开关 | 说明系统为何这样行动 |

例如，评委看到的面板可以是：

```text
当前动作          DEFER / 等待
候选问题          持续偏离当前论点
任务边界          正在发言
提示预算          还可提示 2 次
冷却剩余          0 秒
处理依据          等待当前表达结束，再检查是否仍需提醒
```

这里的“正在发言”来自可观察事件，不需要声称读出了用户的认知负荷。

原型里已经可以调整冷却、提示预算和连续偏题窗口，也可以关闭过程提醒。**这些控件确实影响后续行为，不是装饰性的参数展示。**

我的初始设计是：一次只显示一张提示、默认冷却 12 秒、主动提醒预算 3 次。这些只是便于体验的起始配置，不是必须坚持的产品规则。

# 五、后复盘：回到一个具体时刻，而不是生成一篇总结

复盘页的标题可以是：

> **回到关键时刻，让下一次有一个具体的改变。**

它不是“本次演讲 83 分”，而是一条可以点击的事件时间线。

## 一个事件卡片的完整内容

以第一次偏题为例：

**发生了什么**

> 00:42，你开始介绍与主论点暂时无关的经历。

**系统当时怎么处理**

> 发现候选问题，但没有立即提醒。

**后来发生了什么**

> 00:49，你主动说“回到产品本身”，重新开始介绍方案。

**最终决策**

> 取消提示，因为它已经没有必要。

这个卡片呈现的不是“AI 对你进行了成功纠正”，恰恰是：

**你自己完成了调整，AI 没有抢走这个过程。**

另一个事件则可以呈现真正发出的提示，以及提示之后观察到的发言。

## 复盘必须能继续进入练习

事件详情旁放一个按钮：

### 「重练这个片段」

点击后，不是返回首页重新填一遍资料，而是进入一个短练习：

> **本轮目标：用一句转折，把刚才的例子重新接回主论点。**

保留必要上下文，给用户再尝试一次的空间。

原型中已经有事件查看和新的 30 秒局部练习入口。目前回放的是**文字与事件**，不是录制视频。

这样，教育愿景就体现在交互里：

**不是只告诉你刚才哪里不好，而是把刚才的经历变成下一次可以练习的内容。**

# 六、第二场景：做算法题时，AI 不替你把题写完

算法部分我建议先限定为一个清晰的小场景：

## 二分查找：遗漏最后一个候选元素

用户看到题目、编辑器和测试结果。右侧仍是同一个决策观察窗。

![RealtimeGuide 算法练习原型](sandbox:/mnt/data/realtimeguide-code.png)

第一版不用屏幕识别来“看代码”。既然编辑器就在 Web 内，直接获取代码变更、运行结果和测试事件即可。

## 完整交互故事

用户写出闭区间二分查找，但循环条件使用：

```javascript
while (left < right)
```

运行测试后，出现一个明确反例：

```text
输入：[5]，目标：5
期望：0
实际：-1
```

系统知道**这个版本的代码确实存在失败用例**，但不立即改代码。

### 分支 A：用户正在自行修复

用户继续修改，重新运行后全部通过。

系统取消旧提示，记录：

> 用户已经通过新的测试结果解决当前问题，不再发送之前准备的指导。

### 分支 B：失败仍存在，出现合适窗口

系统给出一个问题：

> **只剩一个元素时，循环还会执行吗？**

它没有直接说“把 `<` 改成 `<=`”，也没有贴出完整答案。

用户可以继续思考，也可以主动点“我需要一点提示”。

**演讲里的“偏题后自行回归”，在算法里对应“失败后自行修复”。两者体现的是同一种教学交互。**

## 算法场景中特别要避免的行为

不要因为用户停了几秒就认定他不会做；不要在用户输入一半代码时不断报错；不要拿旧版本代码的诊断提醒已经修改后的代码。

因此，算法事件需要绑定**代码版本**。显示提示前，必须确认它仍然针对当前代码。

原型中的测试是真实执行：初始示例通过 4/6 个测试，修复边界后通过 6/6；同时有无限循环超时终止。它只是本地练习执行器，不是生产级安全沙箱。

# 七、两个场景共享什么：Jev 判断，Pi 组织，控制器决定是否显示

架构不需要在用户面前讲得复杂，但实现上要有清楚边界。

```text
演讲：转写、提纲、时间、用户操作
算法：代码版本、编辑事件、测试结果
                 ↓
            统一任务状态
                 ↓
       快速判断 + 深入分析
                 ↓
             指导候选
                 ↓
            干预控制器
        ↙        ↓         ↘
      等待      显示       取消 / 记录
                 ↓
          事件复盘 → 局部重练
```

### Jev-like：回答边界清楚的小问题

例如，最近几个片段是否持续偏离当前论点？用户是否已经回到目标？当前片段是否在为主论点举例？

Jev 官方接口的基本形态就是输入状态与类型化问题，得到结构化判断；官方也建议把复杂判断拆成原子问题，再由程序组合。([TypeSafe](https://docs.typesafe.ai/introduction))

### Pi：承担较完整的辅导过程

例如，组织演讲目标、查看事件证据、解释算法反例、生成复盘、构造下一轮局部练习。

Pi 官方的 `pi-agent-core` 提供工具调用和状态管理，可以作为这部分的运行底座。正式接入时应只暴露必要工具，而不是把任意文件、进程和网络权限交给陪练 Agent。([GitHub](https://github.com/earendil-works/pi))

### 干预控制器：掌握最终展示权

即使模型已经生成建议，也要检查：

**证据是否仍有效、用户是否允许、提示是否过期、是否处于冷却、预算是否耗尽。**

因此，“模型判断有问题”不等于“用户马上看到弹窗”。

这份源码包里包含了应用级接口设计，便于后续接入或更换模型，不把产品交互绑定到某一家模型。

# 八、比赛现场怎么展示这套 MVP

我建议用**演讲讲完整故事，用算法说明可扩展性**，不要让两个场景平分叙事。

先打开演讲工作区，说清楚自己的目标。让评委看见第一次偏题时系统等待、随后取消提醒；第二次需要帮助时，一条短提示出现。演讲结束后，直接点击那次“取消”事件，再进入局部重练。

然后切到算法工作区：

> “刚才是在表达中给用户留出自行调整的空间。同样的机制，也可以发生在解题中。”

运行测试，展示反例；修改后，准备中的提示取消。再展示一次最小问题式提示。

最后落到一句话：

> **我们不是让 AI 在每个错误发生时都接管任务，而是让它陪着人完成任务，并把经历变成下一次练习。**

这既保留了教育愿景，也让评委确实看到了一个完整产品，而不是只看到了架构图。

## 一、现版为什么显得“设计感不足”？

看过两张原型截图后，我认为问题主要不是配色，也不是缺少某个动画库。

### 1. 有组件，没有真正的画面构图

目前标题、步骤条、说明、视频、参数、日志都被放进了相近的容器。它们各自合理，但组合起来像一个功能清单。

尤其是演讲页面，用户真正要做的事情--**站在镜头前表达**--只是页面中间的一张卡片。周围还有很多正在要求被阅读的内容。`realtimeguide-live.png`

新的设计应当先决定：

> **这一屏的主角是谁？其他东西应该退到哪里？**

演讲时主角是用户，算法练习时主角是代码，复盘时主角是那次具体经历，而不是系统功能。

### 2. 所有模块使用了相近的视觉重量

深色背景、薄边框、圆角、薄荷绿、小字号--这些并不难看，但覆盖所有模块后，反而缺少主次和记忆点。

算法页面也沿用了类似结构，编辑器、题目、观察窗和测试结果没有形成足够明确的工作空间关系。`realtimeguide-code.png`

**统一不等于所有东西看起来一样。** 同一个设计系统应该允许主舞台、工具、证据和设置拥有不同的视觉角色。

### 3. 页面之间没有连续的视觉叙事

现在是“进入练习页”“进入复盘页”，但用户很难从视觉上感受到：

> 我正在回看刚才那一次经历。

我们需要保留一些跨状态存在的对象：同一个演讲画面、同一条时间轨迹、同一个事件标记。它们在不同阶段重新组织，而不是全部消失后换另一套卡片。

### 4. 太像技术演示的控制台

参数、状态机和脚本控制确实要展示，但不应该成为默认产品气质。

**观察台可以精密，练习空间应该有吸引力。** 两者需要共享系统，但不能共享全部视觉密度。

## 二、调研里真正值得借鉴的六类设计

### 不是找一种“最新风格”，而是分别研究构图、材质、动效和交互

| 参考对象 | 真正值得借鉴的东西 | 应用到 RealtimeGuide | 不应照搬的东西 |
|---|---|---|---|
| **Linear** | 信息密度下的主次、弱化界面外壳 | 让任务占据主视觉，观察工具退后 | 深色 SaaS 模板 |
| **Apple Liquid Glass** | 内容层与控制层的分离、材质与运动统一 | 悬浮 HUD、控制条、观察抽屉 | 整页玻璃和过度透明 |
| **Material 3 Expressive** | 通过尺度、形状、颜色建立重点和情绪 | 开始练习、选择挑战、完成后的关键动作 | 把手机 UI 放大到 PC |
| **Lusion** | 完整视觉世界、3D 与排版协同、连续转场 | 品牌对象、进入练习、进入复盘 | 把工作软件做成漫游展厅 |
| **IBM Carbon Motion** | 日常操作与重要时刻使用不同动效强度 | Live 安静，阶段转换有表现力 | 全部组件使用同一种弹性 |
| **Rive / 状态型动效** | 动画由真实状态驱动，而不是自动播放 | 等待、取消、提示的可视化 | 永远旋转的“AI 正在思考” |

这些不是抽象参考，背后有几项直接影响我们设计的发现。

### Linear：不是“越简洁越好”，而是不要平均分配注意力

Linear 在 **2026 年 3 月的界面更新复盘**中，明确讨论了降低导航的视觉权重、减少无必要的边界，让用户当前工作的内容更加突出。它不是减少功能，而是重新安排视觉优先级。([Linear](https://linear.app/now/behind-the-latest-design-refresh))

对我们最有用的转换是：

**不是删掉参数，而是不要让参数和演讲画面争夺同一个视觉中心。**

### Apple：值得学的是功能分层，不是毛玻璃滤镜

Apple 的 Liquid Glass 介绍把材质、运动和环境适配作为一个整体；控制与导航形成浮在内容之上的功能层。([Apple Developer](https://developer.apple.com/videos/play/wwdc2025/219/))

我会把这个思路用于短提示、底部控制条和观察抽屉。

但代码、转写、复盘正文应该仍然清楚稳定。摄像头背景随时变化，不能为了透明效果让文字忽明忽暗。

**有玻璃质感，不等于所有表面都应该透明。**

### Material 3 Expressive：表现力不必与可用性对立

Google 将颜色、形状、大小、运动和内容分组列为表达性设计的核心手段，用它们强化重要行动。([Google Design](https://design.google/library/expressive-material-design-google-research))

这提醒我们：低干扰产品不必长得像一台没有情绪的仪器。

准备练习时可以有大胆构图；进入挑战可以有仪式感；完成一次练习后可以有明确的情绪释放。问题在于**把表现力放在哪些时刻**，而不是要不要表现力。

### Lusion：真正的设计感来自一整套视觉世界

Lusion 的 Oryzo 制作复盘很值得读。他们并没有停留在“漂亮的抽象 3D 产品”，而是把产品放进一个有情境的场景，再统一处理排版、颜色和转场。([Lusion](https://blog.lusion.co/oryzo-bts-part-3-7-website-ux-ui-and-illustrations))

这对我们的启发不是“做一个类似的 3D 模型”，而是：

> **RealtimeGuide 应该有一个贯穿体验的视觉母题，而不是每页换一个漂亮组件。**

## 三、我建议的艺术方向：空间工作室，而不是赛博后台

结合你之前对 PC 原生界面、大画幅和空间层级的偏好，我会把三个方向组合起来：

**工作区借鉴精密工具的秩序；准备与复盘借鉴编辑式排版；关键转场借鉴高质量实时 3D 的空间连续性。**

不是整套游戏化，也不是全程冷冰冰。

### 准备阶段：开放、有期待感

背景可以偏暖白，使用较大的中文标题、少量精确的说明和一个有材质的空间对象。

第一眼应该看到：

> **把下一次，讲得更好。**

其次才是本次目标和开始按钮。

这里可以让画面更有张力，形成“我要开始一次认真练习”的感受。

### 实时阶段：深色、沉浸、稳定

进入练习后，画面转为深色的主任务空间，外围 UI 收拢。用户本人或代码成为主角。

不是简单切换深色主题，而是**空间被重新分配给当前任务**。

### 复盘阶段：清晰、可阅读、有证据感

结束后，不需要继续保持高度紧张的 HUD 气质。

让转写、事件、代码差异和下一步练习有更好的阅读条件。可以采用同一套设计中的暖灰内容表面，而不是到处黑底荧光字。

### 具体视觉语言

我建议以**墨黑、暖白、一个偏钴蓝的品牌色**为基础，薄荷绿用于完成状态，琥珀色用于确实需要被展示的注意状态。

这不是最终色板结论，而是比“所有地方都是薄荷绿深色卡片”更有角色区分的起点。

材质也分角色：

- **主内容：** 哑光、稳定、可阅读。
- **临时控制：** 少量半透明，有明确的前后关系。
- **品牌对象：** 真正具有体积、光照和材质的 3D。
- **数据证据：** 简洁精确，不通过发光包装可信度。

**高级感应该来自关系、比例和完成度，不是来自把每个元素都做得复杂。**

## 四、一个值得做成品牌记忆的对象：Trace，练习的轨迹

我不建议再用一个漂浮的 AI 球体作为中心。

它很容易表达“这里有人工智能”，但很难表达我们的具体产品理念。

我建议设计一个可折叠、可展开的**轨迹对象**：

### 准备时，它是一个空间结构

可以是一条具有厚度、局部半透明材质的带状结构，在画面中形成清晰的前后关系。

它不是要模拟人的大脑，而是表达一次练习有展开、有转折、有回看。

### 练习时，它收拢为时间与章节轨道

同一个视觉对象变成稳定的时间线，承载经过时间和章节进度。

此时不再持续旋转，也不根据所谓“情绪”随机变形。

### 复盘时，它展开为具体事件

演讲结束，时间轨道变成可探索的事件线。刚才出现过的提示、用户自行解决的问题，都有自己的位置。

点击一个事件，它展开为证据与重练入口。

### 重练时，选中的事件成为新的起点

用户不用重新经历整套配置。画面从这个事件连续返回练习状态。

**这使 3D、Motion 和产品机制成为一件事，而不是互相独立的装饰。**

需要明确：这条轨迹表示的是会话和事件，不是未经测量的“能力成长曲线”。

## 五、四个核心画面应该怎样重新设计？

### 1. 准备页：从表单页变成可操作的第一屏

不要做一个需要滚动很久的宣传首页，也不要第一眼给用户十几个输入框。

画面左侧是大标题、当前目标、演讲／算法场景选择；右侧是轨迹对象。主要操作只有一个：**开始这次练习**。

修改时长、提纲、辅助模式时，相关设置从这个入口附近展开。用户始终能看到自己在准备什么，而不是进入另一个配置后台。

这里的 3D 允许少量视差或指针响应，但**开始按钮必须立即可用，不能等开场动画结束**。

### 2. 演讲页：真正的 Live Stage

默认页面应该以视口为单位，而不是一个越往下越长的后台。

顶部压缩为一条会话栏：名称、时间、设备状态和结束入口。中央给摄像头或演讲内容一个明显的主舞台。

提示位置固定。它不是每次从随机角落冒出来的通知，而是一个可预测的辅助位置。

例如，需要提示时：

> **回到核心：AI 何时该介入？**

文案一次完整出现，不使用逐字输出。提示是为了被迅速理解，不是为了展示模型生成过程。

转写、日志和参数默认不在主视野里。用户可以主动打开，但不要求一直阅读。

### 3. 观察模式：像专业工具，不像数据墙

你希望参数能展示出来，这一点保留，而且可以做得更漂亮。

不过，与其摆十张统计卡片，不如把最重要的机制做成一条清楚的路径：

**发现候选 → 等待 → 用户自行修正 → 取消**

另一次则是：

**发现候选 → 等待 → 出现合适窗口 → 提示**

关键节点能展开证据，参数则放在旁边的精简列表里。

这样评委看到的是**系统行为如何形成**，而不是一排没有解释的数字。

观察模式由用户或演示者明确开启。它可以让舞台平滑让出一部分空间，但在小视口上应使用抽屉或独立观察页，不能把所有模块压成细栏。

### 4. 复盘页：从报告列表变成经历回看

结束演讲后，主舞台缩成证据区域，时间轨道展开，关键事件出现在原来对应的位置。

用户点到“00:49 自行回归”时，看到的是：

> 这里系统已经产生候选提醒，但你自己回到了主题，所以提醒没有出现。

这比一个“本次 86 分”的大圆环更能体现产品。

右侧的主按钮是：

> **重练这个转折。**

如果没有录制视频，就用文本和事件证据，不做一个看起来能回放视频的假播放器。

## 六、Motion：要设计“动作语言”，不是套入场动画

IBM Carbon 将动效区分为支持效率的 *productive motion* 和用于重要时刻的 *expressive motion*。这套区分非常适合我们：日常交互低显著度，关键阶段有表现力。([Carbon Design System](https://www.carbondesignsystem.com/building-blocks/foundations/motion/overview))

同时，Emil Kowalski 的交互动效示例强调：展开应当有来源，缓动应当符合具体操作，不是每个东西都加同一种弹簧。([Emil Kowalski](https://emilkowal.ski/ui/good-vs-great-animations))

我建议建立以下动作语言。表中的时间是**设计初值，不是实测结论**。

| 状态变化 | 学习者看到什么 | 观察者看到什么 | 动效建议 |
|---|---|---|---|
| 开始练习 | 设置收拢，任务画面成为主舞台 | 按需保留观察层 | 450-700 毫秒的空间重组 |
| 正常练习 | 稳定画面和必要的设备状态 | 真实事件更新 | 不做持续装饰运动 |
| 发现候选、决定等待 | **没有新的视觉提醒** | 候选进入等待节点 | 仅观察层轻量过渡 |
| 用户自行修正 | **继续保持安静** | 候选收拢为取消事件 | 不庆祝、不闪绿 |
| 决定提示 | 固定锚点展开一条短建议 | 记录真正展示时间 | 160-240 毫秒，文字完整出现 |
| 进入复盘 | 同一个画面和时间轨迹重新组织 | 展开事件证据 | 450-700 毫秒 |
| 局部重练 | 从所选事件回到练习空间 | 清楚标记新一轮 | 300-450 毫秒 |

### 一个非常关键的设计约束

**如果系统决定不提醒，却让用户看到琥珀色光环、呼吸变快或图标抖动，那它实际上仍然提醒了用户。**

所以，`DEFER` 和 `CANCEL` 在学习者视图中应当真正安静。

我们可以把这些过程做得很有表现力，但要放在**观察模式和事后复盘**里。

这甚至比泛泛的“低干扰设计”更重要：它让视觉语言遵守了产品自己的理念。

### 三段最值得打磨的标志性转场

**第一段：进入练习。**  
空间轨迹收拢，设置退后，演讲画面展开。用户感到自己进入了一个新的任务阶段。

**第二段：提示出现。**  
一个固定的辅助锚点短暂展开为可读建议，再回到原位。建议不是凭空出现的系统通知。

**第三段：进入复盘。**  
刚才的时间轨道成为事件线，刚才的主画面成为证据窗口。用户能直观看出：正在回看的就是刚才发生的事情。

这三段比几十个 hover 特效更值得投入。

---

## 七、3D：可以真做，但要分清三种用途

### 第一层：结构深度--整个产品都应该有

包括前后层次、表面阴影、遮挡、局部透明、进入和退出方向。

很多结构深度用 CSS 和 SVG 就能完成。**空间感不等于必须开启 WebGL。**

例如观察抽屉从舞台旁边展开、提示位于内容之上、复盘事件从时间线上抬起，都可以形成明确的空间关系。

### 第二层：品牌与叙事对象--值得真正做 3D

准备页的轨迹对象、局部材质、少量镜头变化，可以使用真实 3D。

重点应放在材质与光照的一致性，而不是多放几个模型。它需要与字体、颜色、背景共同构图，不能只是页面右边嵌入一个会转的物体。

### 第三层：更前沿的渲染--研究，但不把它变成目标

Lusion 在 Oryzo 中尝试了 **Gaussian Splatting 与传统几何、纹理的混合方案**，不是把整场景都交给一种技术。官方复盘明确描述了只让部分物件和反射采用 splats，其余部分使用更简单的方法。([Lusion](https://blog.lusion.co/oryzo-bts-part-2-7-3d-design-and-motion-graphics))

这值得参考，因为它说明：

> **前沿不是“所有东西都用最复杂的方案”，而是知道每种方案应该负责哪一部分。**

对我们的下一版，真实 3D 品牌对象已经足以建立差异，不需要先造一个完整虚拟教室。

WebGPU 也类似。Three.js 的新渲染器支持 WebGPU，并提供 WebGL2 回退，但具体材质、后处理与框架组合仍需验证。它可以进入技术探索，不必成为第一版视觉质量的前提。([Three.js](https://threejs.org/manual/pages/webgpurenderer?utm_source=chatgpt.com))

---

## 八、算法场景也要有设计，但不能为了统一强行 3D 化

算法页应该更接近一个认真工作的练习工作室，而不是把演讲页的视频卡片换成编辑器。

我建议：

**代码占据主空间，题目在可调宽侧栏，运行结果在可展开的底部，提示在固定辅助位置。**

可以把“二分查找的候选区间”做成简洁的二维或轻度空间化可视化：当前区间、边界和最后一个元素清楚地变化。

但不能让代码透视倾斜，也不能让数组为了“3D 效果”变得难以比较索引。

这里更值得做的动效是：

- 运行后，失败用例与对应输入建立明确关系；
- 点击用例，打开相关代码版本，而不是跳去无关页面；
- 用户修复后，旧候选在观察窗中取消；
- 复盘时，前后两个版本之间的差异被清楚呈现。

**两个场景共享的是视觉语言、事件连续性和指导机制，不是每一屏都长得一模一样。**

---

## 九、落地技术：不要为了“集百家之长”把库全部装进来

我建议下一版主干使用：

**React + TypeScript + Motion + Three.js / React Three Fiber + CSS/SVG。**

其中，Motion 的布局动画和 `layoutId` 适合连接同一对象的不同状态，例如主舞台变成复盘证据窗、时间线事件展开为详情。([Motion](https://motion.dev/docs/react-layout-animations))

Rive 可以作为状态型品牌组件的备选。它的状态机适合把交互状态和动画连接起来，但不需要为了一个简单图标就引入新的制作流程。([rive.app](https://rive.app/docs/editor/state-machine))

GSAP 更适合复杂的跨对象序列编排；只有真正需要精确镜头与多层时间轴时再加入，并且避免与 Motion 同时控制同一个元素属性。其 Timeline 本身支持对整组动画进行统一的播放、暂停和定位。([GSAP](https://gsap.com/docs/v3/GSAP/Timeline/))

原生 View Transitions 也值得利用，它可以在不同页面状态间匹配同一对象，建立连续过渡；应作为有特性检测和降级方案的增强，而不是阻断操作的依赖。([Chrome for Developers](https://developer.chrome.com/docs/modern-web-guidance/guides/ui-behaviors/same-document-transitions))

### 性能本身也是设计的一部分

这里有一个针对我们场景的实际约束：摄像头、转写、编辑器和动效可能同时运行。

所以我会规定：

**装饰性 3D 在 Live 阶段停止或静止；关键文本与操作留在 DOM；离屏时不继续渲染；用户操作不等待动画播完。**

React Three Fiber 官方文档提供了按需渲染、资源复用等方案，适合让场景停下来后不再持续消耗渲染资源。([r3f.docs.pmnd.rs](https://r3f.docs.pmnd.rs/advanced/scaling-performance))

同时保留减少动态效果模式：移除大幅缩放、视差和镜头运动，用短淡入或直接状态切换保留功能。Motion 对此有现成支持。([Motion](https://motion.dev/docs/react-accessibility))

这不是降低视觉标准。**一个漂亮但掉帧、挡住输入或让用户等动画的界面，本身就是没有完成的设计。**

## 十、下一版应该怎么推进？

我不建议直接在旧 HTML 上继续加阴影、渐变和动画类名。

**第一步，先做三张高保真关键画面：准备、Live、复盘。**  
在没有动画时，它们就应该有清晰构图和品牌辨识度。静态画面不成立，动画通常只会放大问题。

**第二步，做一段可反复触发的完整动效样机。**  
只围绕进入练习、等待与取消、提示、复盘、重练这条链路打磨。这样可以检查整体节奏，而不是分别欣赏几个孤立特效。

**第三步，再把已有状态机和真实事件接进去。**  
业务状态决定视觉，不能反过来让动画时间轴决定什么时候提醒、什么时候采集或什么时候结束。

我的最终建议是：

> **让入口有吸引力，让任务空间有沉浸感，让关键转场有记忆点，让复盘有连续性。**
>
> **但当用户真正开始表达或思考时，界面知道退后。**

这才是 RealtimeGuide 值得拥有的设计辨识度：不是“一个很酷的 AI 控制台”，而是**一个有表现力、又懂得把注意力留给人的训练空间。**

## 一、重新定义 Less is More：少的不是像素，而是额外的认知工作

这点非常重要。

把十句话缩成三个陌生图标，虽然界面更空，却可能要求用户花更多精力猜测。反过来，一句明确的“还剩 30 秒”，可能比一圈含义不清的动态光环更容易理解。

所以我们的设计原则不是：

> 所有内容都尽量短，所有组件都尽量少。

而是：

> **用户为了获得这次帮助，需要额外注意、理解、判断和操作多少？能不能更少？**

这也解释了你说的：有时图形更好，有时运动更好，有时文字反而最好。

**媒介不是品牌偏好，而是根据当前需要传达的内容来选择。**

| 需要传达的内容 | 更适合的表达 | 不应该怎样做 |
|---|---|---|
| 还剩多少时间 | 固定位置的时间或简单刻度 | 一直跳动、闪烁，持续索取注意力 |
| 下一步应回到哪个论点 | 一句短而具体的文字 | 用一个抽象图标让用户猜 |
| 二分查找中还剩哪个候选元素 | 数组、区间与边界的直接标记 | 先给一大段算法解释 |
| 一个事件如何从等待变成取消 | 在 Underlying 中用连贯动效表达 | 让学习者也看到候选反复变化 |
| 为什么当时选择不提醒 | 复盘中的证据与简短解释 | 在演讲过程中展开推理说明 |

**Less is More 不是拒绝丰富表达，而是拒绝没有必要的处理负担。**

---

## 二、Focus：AI 存在，但不要求你关注它

默认界面应该由用户的任务决定，而不是由我们的模型架构决定。

### 演讲时，界面首先是一场演讲

主画面是摄像头预览或用户的演讲内容。保留清晰的开始、暂停、结束入口，以及必要的设备采集状态。

剩余时间可以按用户选择显示。提纲可以收起。参数、判断信号和事件日志不出现。

**平时不需要一个持续旋转的 AI 球体，也不需要“正在分析你的表达”的状态文字。**

摄像头、麦克风是否开启属于知情与控制信息，需要保留；模型有没有产生一个新的候选判断，则不需要用户随时知道。

真正需要指导时，在一个稳定、可预测的位置出现一条信息：

> 回到主线：为什么需要实时指导？

提示出现以后，给用户足够时间理解，然后退出。不会继续堆第二条、第三条，也不会因为系统又计算了一次就换一种说法。

### 做算法题时，界面首先是一个工作区

题目、代码、测试结果是主内容。系统不能为了展示自身存在，不断在编辑器周围添加动态信号。

用户主动运行测试，失败结果正常呈现——这是用户请求的任务反馈，不是 Agent 的主动干预。

Agent 的额外指导则需要另作判断。例如，在合适时机给出：

> 只剩一个元素时，循环还会执行吗？

必要时，配合一个小的区间示意，比再弹出一整张解释卡片更直接。

**同一个产品，不需要在所有场景中维持同一种 HUD。它需要维持的是同一种克制。**

---

## 三、“合适的时空和形式”应该成为干预决策的一部分

此前我们主要讨论的是“提醒还是不提醒”。现在需要进一步扩展：

**一次指导决策，不只决定内容，还决定它何时出现、出现在哪里、用什么形式、持续多久，以及什么时候失效。**

这意味着视觉设计不能只是最后给模型答案套一个 UI。

例如，系统发现演讲持续偏离主题：

- 现在仍在连续表达：暂不呈现。
- 出现合适窗口，但用户已经回归：取消，不再呈现。
- 窗口出现，问题仍然存在：显示一条具体的回归建议。
- 演讲已经结束：不补发提示，把事件交给复盘。

这里最重要的约束是：

### 不提醒，就必须真的不提醒

如果系统选择等待，却让屏幕边缘变黄、AI 图标加快呼吸、轨迹开始抖动，那么它实际上已经打断了用户。

因此在 Focus 中：

**发现候选、等待、取消，都可以没有任何视觉变化。**

这些状态的表现力，应当留给 Underlying 和复盘。

同样，动画不能人为推迟一条已经需要出现的信息。提示文字应及时、完整地可读，不能为了优雅入场先播放一段两秒钟的演出。

## 四、Underlying：不是调试面板，而是一张可读的运行图

这里可以有非常鲜明的艺术性。

但它的美感应该来自：**真实事件之间的关系，被有秩序地呈现出来。** 而不是一堆随机流动的粒子和数字。

我建议把 Underlying 的核心概念定为：

> **展开同一次任务背后的决策过程。**

用户点击一个安静的入口，例如“查看内部”，界面才展开。它不是换到一套无关的后台，而是仍围绕当前这场演讲、当前这段代码。

### 先展示一件事：系统此刻在做什么

Underlying 第一层不应该立刻出现所有参数。

首先让人看懂当前事件：

> 检测到主题偏离候选。  
> System 1 建议继续观察。  
> Controller 暂不显示提示。  
> System 2 尚未被调用。

这已经比几十个统计数字更能解释系统。

随后，用户可以选择某个事件，逐步展开判断信号、调用记录和配置参数。

**Underlying 本身也遵守 Less is More，只是它此时服务的任务变成了“理解内部机制”。**

---

## 五、System 1 和 System 2，如何艺术性地呈现？

我不建议用两个发光的大脑，或者两个不断自转的球体。

更合适的是：**同一条时间轴上的两种工作节奏，加上独立的干预控制层。**

| 层 | 视觉表达 | 显示的信息 |
|---|---|---|
| **System 1：快速判断** | 紧凑的事件节点；每次真实判断形成一个短小、可追踪的变化 | 输入事件、判断类别、候选动作、调用耗时 |
| **System 2：深入分析** | 按需展开的局部分支；证据、工具和结果逐步出现 | 分析任务、使用的证据、工具状态、指导候选 |
| **Controller：干预仲裁** | 清楚的动作节点，连接到真正的界面输出 | 等待、取消、提示、仅记录，以及对应规则 |

### System 1 的“快”，不是让动画快到看不清

它可以表现为短、频繁、局部的节点变化，但每个节点都能停下来查看。

事件过多时聚合显示数量，不把整张画面做成高速刷新的终端。

### System 2 的“深”，不是假装生成一段思维独白

用可验证的工作呈现深度：

> 收到分析任务 → 读取最近发言 → 对照提纲 → 生成指导候选。

工具调用确实开始了，节点才进入运行状态；结果确实返回了，才出现对应结果。没有被调用时，它保持安静。

这里展示的是**任务状态、证据、工具结果和简短决策依据**，不是编造模型的“内心活动”。

### Controller 必须有独立的存在感

这是我们技术展示中最值得保留的一层：

**模型认为值得关注，不等于用户就会收到提醒。**

观众应该能亲眼看见：一个候选已经产生，却因为用户自行修正而被取消；另一个候选通过时机与有效性检查，才成为 HUD。

而且这不是每次都必须走完的串行流水线。System 2 可以没有参与，两个模型也可以处理不同事件。画面应忠实于实际运行关系。

---

## 六、参数展示：让每个数字回答一个问题

Underlying 需要精密，但不应该成为数据墙。

我建议围绕选中的事件组织参数，而不是永久显示几十张指标卡片。

| 用户想知道什么 | 应展示的参数 |
|---|---|
| 系统看到了什么？ | 输入片段、时间范围、代码版本、测试结果 |
| 判断用了多久？ | 实际请求耗时、排队时间、结果返回时间 |
| 为什么没有提醒？ | 当前动作、冷却剩余、提醒预算、候选有效期、用户设置 |
| System 2 做了什么？ | 已调用工具、任务状态、返回结果、生成的候选 |
| 这次结果还能用吗？ | 事件年龄、目标版本、是否已经失效或被取消 |

模型分数可以展示，但要标明它究竟是什么；不能把一个分类分数包装成“用户认知负荷 82%”。

预置演示与实际运行也应有清楚的数据来源标记。

**参数不必越多越专业。让观众能解释一次决策，比让他们看到一百个数字更有说服力。**

---

## 七、Motion 和 3D 的位置，现在就清楚了

### 在 Focus 中，动效负责减少理解成本

例如，提示从固定位置展开，让用户知道它从哪里来；复盘时，刚才的时间标记连续变成事件，让用户不必重新寻找上下文。

不做无意义的背景漂浮，也不让录音状态、偏题状态和推理状态都各自“呼吸”。

### 在 Underlying 中，动效负责解释运行关系

一个输入被 System 1 接收，一个候选被交给 Controller，一项深入分析展开，一条过期建议被取消。

这些可以有节奏、有材质、有空间感。

**动画不是在宣称“系统很先进”，而是在让运行过程更容易被看懂。**

### 3D 只在它有助于表达层级时出现

例如，把“任务事件”“快速判断”“深入分析”“实际干预”组织成有前后关系的几个层面。主动展开 Underlying 时，这些层面轻微分离。

但文本仍保持正面可读，参数不悬浮在需要旋转寻找的位置，不要求用户拖动镜头才能找到某次调用。

可以理解为：

> **空间用于解释关系，平面用于阅读信息。**

这比一个自由漫游的 3D 控制室更符合我们的产品。

## 八、最好的展示，是同一时刻的两个视角

设想一次演讲中的短暂偏题。

**演讲者看到：**  
画面没有变化。他继续表达，随后自己回到主题。

**Underlying 的观察者看到：**  
输入事件到达 → 偏离候选产生 → Controller 等待 → 新发言表明已经回归 → 候选取消。

然后发生另一次持续偏题。

**演讲者看到：**  
在合适时机，一条短提示出现。

**Underlying 的观察者看到：**  
候选仍有效 → 当前允许提示 → HUD 实际展示 → 进入冷却。

这正是产品和技术最有力量的结合：

> **对用户而言，只发生了一次恰到好处的帮助。**
>
> **对观察者而言，可以看见这次帮助背后的选择。**

真正路演时，还可以把两种视角放在不同屏幕：演讲者保持 Focus，评委观看 Underlying，避免为了展示技术而破坏正在展示的低负荷体验。
