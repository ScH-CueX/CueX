## Decision

Use the supplied SSH access to deploy one of the named models. Both the product voice and film voice must use that deployed service. Do not silently replace its output with Edge or another provider if it fails.

## Implementation boundary

Preserve the supplied pinned host-key verification. Keep credentials outside the repository and deliverables. Use a dedicated model environment and directory after inspecting the machine. Reuse the project's existing POST text → audio adapter and its cancellation behavior. Do not change SSH users, host keys, firewall rules or unrelated applications. Model choice depends on inspected hardware and official compatibility; this is delegated by the user's two-model choice.

Routine deployment details are implementation choices within the user's authorized scope, not claims of separately approved policies. No boot autostart or global Git hook changes are included.

### Transport refinement (verified host policy)

The Windows model is ready on loopback, but the supplied SSH endpoint rejects direct TCP forwarding (`administratively prohibited`). Keep its SSH policy unchanged. Use the authorized SSH exec channel to run a bounded, fixed-endpoint HTTP request helper; expose the same HTTP contract only on the Mac's loopback. Each request owns its SSH process, abort discards its response, only `/health` and `/tts` are supported, and no text is interpolated into shell commands. Reuse a private SSH control socket for connection latency; stop only the bridge's own child processes and control socket. This does not add a public listener or another voice provider.

### Runtime default

The default real TTS engine now uses the Windows HTTP endpoint and `none` fallback. Legacy providers remain explicit opt-in adapters; the normal `demo` command starts the SSH bridge first. This applies the user’s requirement to actual product speech as well as film narration.
